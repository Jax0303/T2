# 제 2 장 관련 연구

본 장에서는 제안하는 방법의 바탕이 되는 연구를 살펴본다. 먼저 검색 증강 생성의 개념과 구성 요소를 설명하고, 문서를 색인 단위로 나누는 방법과 검색 기법, 검색 결과가 LLM의 답에 미치는 영향을 기술한다. 그리고 문서 조각을 계층적으로 요약하여 검색하는 RAPTOR를 설명한다. 마지막으로 계층형 표 질의응답 데이터셋과 표 안 검색, 표를 대상으로 하는 검색 증강 생성 연구를 살펴본다.

## 2.1 검색 증강 생성

### 2.1.1 검색 증강 생성의 개념

검색 증강 생성(Retrieval-Augmented Generation, RAG)은 사전학습된 생성 모델에 외부 문서 검색을 결합하여 답을 생성하는 방법이다. Lewis 등은 사전학습된 생성 모델을 매개변수 기억(parametric memory)으로, 신경망 검색기로 접근하는 위키백과의 밀집 벡터 색인을 비매개변수 기억(non-parametric memory)으로 결합한 생성 모델을 RAG로 정의하였다[1]. 생성 모델이 학습 과정에서 매개변수에 저장한 지식만으로 답하는 것과 달리, RAG는 질문이 주어질 때마다 외부 문서에서 관련 조각을 찾아 생성 모델의 입력에 함께 넣는다.

RAG는 모델을 다시 학습하지 않고도 외부 문서의 내용을 답에 반영할 수 있다는 장점이 있다. 문서가 바뀌면 색인만 다시 만들면 되고, 생성 모델의 매개변수는 그대로 둔다. 이러한 특성 때문에 RAG는 기업이나 기관이 보유한 내부 문서에 대한 질의응답에 널리 쓰인다. 본 논문의 시스템도 공개된 임베딩 모델과 LLM을 학습 없이 그대로 사용하고, 문서의 표만 색인하여 질의응답을 수행한다.

### 2.1.2 검색 증강 생성의 구성 요소

검색 증강 생성 시스템은 [그림 1-2]와 같이 다음의 구성 요소로 이루어진다.

- **문서 조각(Chunk)**: 색인과 검색의 단위이다. 긴 문서를 그대로 LLM에 넣을 수 없으므로, 문서를 일정한 길이나 구조에 따라 조각으로 나눈다. 조각의 단위를 무엇으로 정하는지에 따라 검색되는 정보의 범위와 LLM 입력의 길이가 달라진다.
- **임베딩 모델(Embedding Model)**: 문장을 고정 차원의 벡터로 바꾸는 모델이다. 의미가 비슷한 문장은 벡터 공간에서 가까운 위치로 표현되므로, 두 벡터의 코사인 유사도나 내적으로 문장 사이의 의미 유사도를 계산할 수 있다.
- **벡터 데이터베이스(Vector Database)**: 문서 조각의 벡터를 저장하고, 질문 벡터와 유사도가 높은 벡터를 찾아 주는 저장소이다. 조각 수가 적으면 모든 벡터와의 유사도를 직접 계산하고, 조각 수가 많으면 근사 최근접 탐색을 사용한다.
- **검색기(Retriever)**: 질문이 주어지면 질문과 문서 조각의 유사도를 계산하여 순위를 매기고, 상위 몇 개의 조각을 고르는 구성 요소이다. 임베딩 벡터의 유사도뿐 아니라 단어 일치에 기반한 점수를 함께 쓰기도 한다.
- **대규모 언어 모델(LLM)**: 질문과 검색된 조각을 입력받아 답을 생성하는 모델이다. LLM은 입력에 들어 있는 정보를 바탕으로 답하므로, 답에 필요한 정보가 입력에 빠져 있으면 답을 맞힐 수 없다.
- **답변 검증(Answer Verification)**: 생성된 답이 검색된 조각에 근거하는지, 질문에 맞는지를 확인하는 단계이다. 검증을 통과한 답은 사용자에게 반환하고, 통과하지 못한 답은 다시 생성하게 한다. 이 단계는 선택적으로 사용된다.

### 2.1.3 문서 분할과 색인

문서 분할은 문서를 색인 단위인 청크로 나누는 과정이다. 가장 널리 쓰이는 방식은 문서를 정해진 글자 수나 토큰 수 이하의 청크로 자르는 고정 길이 분할이다. 청크 경계에서 문장이 끊기는 문제를 줄이기 위해 이웃한 청크가 일정한 길이만큼 겹치도록 자르기도 한다.

LangChain의 공식 RAG 튜토리얼은 이러한 구성을 그대로 보여 준다[2]. 튜토리얼은 문서를 RecursiveCharacterTextSplitter로 청크 크기 1,000자, 겹침 200자로 나누고, 각 청크를 임베딩하여 벡터 저장소에 넣는다. RecursiveCharacterTextSplitter는 문단 구분, 줄바꿈, 공백의 순서로 구분자를 바꾸어 가며 각 청크가 지정한 길이를 넘지 않도록 자른다. 튜토리얼의 RAG 체인 예제는 질문이 주어지면 벡터 저장소의 유사도 검색으로 기본값인 상위 4개 청크를 찾고, 이 청크들을 이어 붙여 질문과 함께 LLM에 전달한다.

고정 길이 분할은 문서의 종류를 가리지 않고 적용할 수 있고 구현이 단순하다는 장점이 있다. 그러나 표를 포함한 문서에 적용하면 표를 마크다운과 같은 텍스트로 먼저 펼친 뒤 글자 수에 따라 자르게 된다. 표의 열 머리글은 텍스트의 맨 위 몇 줄에만 있으므로, 표가 여러 청크로 나뉘면 첫 청크를 제외한 청크에는 열 머리글이 들어 있지 않다.

### 2.1.4 밀집 검색과 희소 검색

검색기가 질문과 문서 조각의 관련성을 계산하는 방식은 크게 밀집 검색과 희소 검색으로 나뉜다.

밀집 검색(dense retrieval)은 질문과 문서 조각을 각각 임베딩 모델로 밀집 벡터로 바꾸고, 두 벡터의 유사도로 관련성을 계산한다. Karpukhin 등은 질문과 문단을 서로 다른 BERT 인코더로 각각 768차원 벡터로 바꾸고 두 벡터의 내적으로 유사도를 계산하는 이중 인코더 구조의 DPR(Dense Passage Retrieval)을 제안하였다[3]. DPR은 여러 공개 도메인 질의응답 데이터셋에서 상위 20개 문단의 검색 정확도가 단어 일치 기반의 BM25보다 9~19%p 높았다[3]. 본 논문에서 사용하는 BAAI/bge-base-en-v1.5는 BGE 계열의 공개 영어 임베딩 모델로, 문장을 768차원 벡터로 바꾼다[4]. 이 모델은 검색에 사용할 때 질문 앞에 검색용 지시문을 붙이고 문서 쪽에는 붙이지 않는다.

희소 검색(sparse retrieval)은 질문과 문서 조각에 나타나는 단어를 기준으로 관련성을 계산한다. 대표적인 방법인 BM25는 질문의 단어가 조각에 자주 나타날수록, 그리고 그 단어가 전체 조각 가운데 드물게 나타날수록 높은 점수를 주며, 조각의 길이에 따라 점수를 보정한다[5]. 희소 검색은 항목 이름이나 연도처럼 질문에 나온 단어가 문서에 그대로 나타나는 경우에 강하다.

하이브리드 검색은 두 점수를 함께 쓰는 방식이다. 두 점수는 범위가 다르므로 각각 정규화한 뒤 가중합하여 최종 점수로 사용한다. 하이브리드 검색은 의미 유사도와 단어 일치를 함께 반영할 수 있다.

### 2.1.5 검색 결과의 잡음과 답변 검증

검색된 조각에는 답에 필요한 정보와 함께 질문과 무관한 내용이 들어갈 수 있다. Cuconasu 등은 정답 문서에 질문과 의미가 비슷하지만 답이 없는 문서를 더하면 LLM의 정확도가 크게 떨어진다는 것을 보였다[6]. Liu 등은 LLM이 입력의 처음이나 끝에 있는 정보보다 입력의 중간에 있는 정보를 잘 활용하지 못한다는 것을 보였다[7]. 표 문서에서는 청크 하나가 수십 개의 셀을 담으므로, 답에 필요한 셀 몇 개를 전달하기 위해 수십 개의 무관한 셀이 함께 전달된다.

생성된 답의 근거를 확인하는 답변 검증도 연구되고 있다. Asai 등은 LLM이 필요할 때만 검색을 수행하고, 반성 토큰(reflection token)이라는 특수 토큰을 생성하여 검색된 조각의 관련성과 자신이 생성한 답이 조각에 근거하는지를 스스로 평가하도록 학습하는 Self-RAG를 제안하였다[8]. Self-RAG는 이 평가를 바탕으로 여러 후보 답 가운데 사실성과 전체 품질이 가장 나은 답을 고른다. 본 논문의 시스템은 답변 검증을 사용하지 않으며, 검색 단계의 색인 단위를 바꾸어 LLM의 입력에 답에 필요한 셀이 들어가도록 하는 데 초점을 둔다.

## 2.2 계층적 요약 기반 검색

고정 길이 분할은 문서 전체에 걸친 내용을 청크 하나에 담지 못한다는 한계가 있다. Sarthi 등은 문서 조각을 계층적으로 요약한 트리를 만들어 검색하는 RAPTOR(Recursive Abstractive Processing for Tree-Organized Retrieval)를 제안하였다[9]. RAPTOR는 먼저 문서를 100토큰 길이의 잎 청크로 나누고 임베딩한다. 이때 문장이 100토큰 한도를 넘으면 문장을 자르지 않고 다음 청크로 옮긴다. 그리고 UMAP으로 임베딩의 차원을 줄인 뒤 가우시안 혼합 모델(Gaussian Mixture Model)로 비슷한 노드들을 군집으로 묶고, 각 군집을 LLM으로 요약하여 상위 노드를 만든다. 요약된 노드를 다시 임베딩하여 군집화와 요약을 더 이상 할 수 없을 때까지 반복하면, 잎 청크부터 문서 전체의 요약까지 이어지는 트리가 구성된다.

검색 단계에서는 트리의 모든 층의 노드를 한데 모아 질문과의 코사인 유사도로 정렬하고, 정해진 최대 토큰 수에 이를 때까지 위에서부터 노드를 골라 LLM에 전달한다. 이 방식을 붕괴 트리(collapsed tree) 검색이라 하며, 원 논문은 최대 2,000토큰의 붕괴 트리 검색을 사용하였다[9]. 붕괴 트리 검색은 질문에 따라 세부 내용을 담은 잎 청크와 넓은 범위를 담은 요약 노드를 함께 고를 수 있다.

RAPTOR를 표 문서에 적용하면 잎 청크는 고정 길이 분할과 같은 방식으로 표의 텍스트를 자르므로, 잎 청크에서도 열 머리글이 분리될 수 있다. 또한 요약 노드는 여러 청크의 내용을 줄여 쓰므로, 개별 셀의 값과 그 머리글이 요약에 남는다는 보장이 없다.

## 2.3 계층형 표와 표 질의응답

### 2.3.1 계층형 표 질의응답 데이터셋

계층형 표 질의응답은 행 머리글과 열 머리글이 여러 층으로 이루어진 표를 보고 질문에 답하는 과제이다. HiTab은 통계 보고서와 위키백과 페이지에서 수집한 계층형 표 3,597개와 질문 10,672개로 이루어진 질의응답 데이터셋이다[10]. HiTab의 표에는 표마다 제목이 주어지며, 질문은 표 안의 셀 값을 조회하거나 여러 셀의 값을 계산하여 답하도록 구성되어 있다.

MultiHiertt는 재무 보고서에서 수집한 문서를 대상으로 하는 수치 추론 질의응답 데이터셋이다[11]. 문서마다 여러 개의 계층형 표와 본문 문단이 함께 들어 있으며, 질문에 답하려면 여러 표와 문단에 흩어진 값을 찾아 계산해야 하는 경우가 많다. 각 문항에는 정답과 함께 답에 필요한 표의 셀과 본문 문장이 근거로 표시되어 있고, 수치 계산이 필요한 문항에는 계산 과정이 프로그램 형태로 주어진다. MultiHiertt의 표에는 제목이나 캡션이 따로 주어지지 않는다. 본 논문은 MultiHiertt를 주 평가 데이터로 사용하고, 캡션의 효과는 HiTab으로 확인한다.

### 2.3.2 표 안 검색

큰 표를 LLM이나 표 질의응답 모델에 그대로 넣으면 입력 길이의 한도를 넘거나 무관한 셀이 많아진다. Lin 등은 표 하나가 주어졌을 때 질문에 필요한 행과 열만 골라 부분 표를 만드는 표 안 검색기(Inner Table Retriever, ITR)를 제안하였다[12]. ITR은 행과 열을 각각 검색 단위로 삼아 질문과 가까운 행과 열을 찾고, 그 교차로 이루어진 부분 표를 기존 표 질의응답 모델의 입력으로 사용한다. 이 방법은 큰 표를 모델의 입력 한도 안에 맞추면서 질문에 필요한 부분을 남긴다.

ITR은 행 하나 또는 열 하나를 검색 단위로 삼으므로, 계층형 표에서 여러 층의 행 머리글과 열 머리글이 함께 정하는 셀의 의미가 하나의 검색 단위 안에 모두 담기지는 않는다. 또한 표 하나를 대상으로 설계되어, 문서 안의 여러 표 가운데 필요한 표를 고르는 단계는 포함하지 않는다.

## 2.4 표 대상 검색 증강 생성

### 2.4.1 TableRAG: 대규모 표를 위한 스키마·셀 검색

Chen 등은 백만 토큰 규모의 큰 표를 LLM이 다룰 수 있도록, 표 전체 대신 스키마와 셀을 따로 검색하여 프롬프트를 구성하는 TableRAG를 제안하였다[13]. TableRAG는 먼저 LLM으로 질문으로부터 열 이름에 대한 검색 질의와 셀 값에 대한 검색 질의를 여러 개 생성한다. 스키마 검색은 열 이름과 자료형, 숫자 열의 최솟값과 최댓값을 담은 스키마 문서를 찾고, 셀 검색은 열 이름과 셀 값의 쌍으로 만든 셀 문서를 찾는다. 마지막으로 찾은 스키마와 셀을 바탕으로 LLM이 표를 조회하는 파이썬 프로그램을 작성하고 실행하여 답을 구한다.

TableRAG의 셀 문서는 열 이름과 값의 쌍이며 행 머리글을 포함하지 않는다. 또한 열 이름 한 줄을 가진 평면 표를 전제로 하므로, 열 머리글이 여러 층이고 행 머리글이 있는 계층형 표에서는 셀 문서가 셀의 의미를 모두 담지 못한다. 그리고 숫자 열의 셀은 개별 값이 아닌 최솟값과 최댓값의 요약으로만 색인되므로, 재무 보고서처럼 대부분의 셀이 숫자인 표에서는 셀 검색으로 정답 셀 자체를 찾기 어렵다.

### 2.4.2 TableRAG: 이종 문서를 위한 검색 증강 생성

Yu 등은 표와 본문이 섞인 이종 문서를 대상으로 하는 검색 증강 생성 프레임워크를 제안하였다[14]. 이 방법은 오프라인 단계에서 문서의 표를 마크다운 형식으로 바꾼 뒤 1,000자 단위의 청크로 잘라 색인하고, 별도로 표를 관계형 데이터베이스에 넣는다. 온라인 단계에서는 LLM이 질문을 하위 질의로 분해하고, 하위 질의마다 청크 검색과 재정렬로 관련 청크를 찾은 뒤 SQL 질의를 생성하여 데이터베이스에서 값을 조회한다. 하위 질의의 답을 모아 최종 답을 낼 때까지 이 과정을 반복한다.

이 방법의 텍스트 검색 경로는 고정 길이 청크 분할이므로 2.1.3절과 같이 청크 경계에서 열 머리글이 분리될 수 있다. SQL 경로는 표가 열 이름 한 줄을 가진 관계형 스키마로 변환될 수 있음을 전제로 하는데, 여러 층의 머리글을 가진 계층형 표는 이러한 스키마에 그대로 대응되지 않는다.
