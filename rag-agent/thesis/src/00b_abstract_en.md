# Abstract

In a hierarchical table, the meaning of a cell value is fixed by a combination of multi-level row and column headers. When a table is flattened or split into rows or chunks for retrieval, cells are separated from their headers, so both the retriever and the reader lose track of what a value refers to. In a closed environment that uses only local models and no external APIs, we retrieve cells by writing one sentence per cell, containing the row header path, the column header path and the value, and indexing these sentences with an off-the-shelf embedding model without training. Writing a cell as a sentence with its header path was first done by MT2Net (Zhao et al., 2022). This study does not train the retriever, extends the header paths so that no two cells in a document share the same sentence, and compares against table-, row- and chunk-level indexes under the same conditions with statistical tests.

On MultiHiertt, we compare the method with a re-implementation of TableRAG's cell retrieval and that paper's baselines (RowCol, RandRow), a heterogeneous-document chunking scheme and fixed-length chunks under the same embedding model, retriever and number of cells passed to the reader (top 20 cells). Cell-level retrieval puts all gold cells into the reader input more often than these baselines (.8634 within the document, Table 5-1). A variant that repeats the leaf labels at the start of each cell sentence (sleaf) scores higher than the method (.8728). With the header rule matched, answer accuracy is higher than with fixed chunks (408 vs 368 of 882, p=.0052); on questions where both methods retrieved all gold cells there is no difference (59:62, p=.86), so the answer difference comes from questions where only one method retrieved them. Answer accuracy is not significantly different from giving the reader all tables of the document (408 vs 378, Holm p=.078).
