| 방법 (출처) | 검색 정확도 | 답변 정확도 | 검색 성공 시 답변 정확도 |

- ours가 세 지표 전부 1위.
- "검색 성공 시 답변 정확도"가 방법마다 벌어짐(.7793→.3594) — 정답 셀을 찾아도 문맥이 조잡할수록(청크/행열 통째) 리더가 정답을 못 뽑아낸다는 뜻. 검색 정확도만으론 안 보이는 차이.
- 같은 계열: self-judge escalation(ours, k=1→필요시 k=20) n=100 답변정확도 0.77 — 정적 k=1(.75), 정적 k=20(.74)보다 나음. 판별기가 escalate 안 한 80건만 보면 0.825, escalate한 20건은 0.55. 판별기 자체 정확도(정말 k=1이 정답이었는지 맞춘 비율)는 0.77 — 완벽하지 않아서 부분집합 수치(.825)를 전체 성능으로 보고하면 안 됨.

¹ **2026-09-20 캐비엇**: 이 arm은 MT2Net(Zhao 2022) 논문의 재현이 아니다. 검색 메커니즘(임베딩+하이브리드 유사도, 코퍼스 전체 대상)은 ours와 완전히 동일하고, 셀→문장 렌더링 템플릿만 논문 Figure 1의 예시 문장 1개에서 구분자·어순을 역추정해 바꿔 끼운 것이다. 그 역추정 자체가 원 예시 문장을 재현하지 못하는 것으로 이미 확인됨(`rag_agent/serialization/templates.py` PROVISIONAL 주석). 원 논문의 핵심 메커니즘(BERT pairwise 분류기, 문서 내부 탐색)은 재현하지 않았다.

³ **2026-09-20 캐비엇**: TableRAG(Chen 2024) 텍스트 표현(범주형 dedup, 숫자열 min/max 요약)은 구글 공식 코드(google-research 저장소 커밋 대조 확인됨)와 맞춘 고신뢰 포트다 — 문장 자체는 신뢰할 만함. 다만 **검색기는 논문의 것이 아니라 ours와 동일한 임베딩+하이브리드 유사도**를 쓴다(`rag_agent/serialization/tablerag_unit.py` 코드 주석이 "구글 TableRAG 시스템 결과로 인용하지 말 것"이라고 스스로 명시). RowCol·RandRowSampling은 TableRAG 논문 자체가 비교 대상으로 쓴 두 baseline이며 재구현이 논문과 대조 확인됨.

⁴ **2026-09-20 캐비엇**: trag_hetero(Yu 2025) 중 재현한 것은 **청킹 표현**(엑셀→마크다운 변환 후 글자 수 기준 분할)뿐이다. 원 논문이 동시에 쓰는 SQL 실행 경로(표 스키마→NL2SQL→실제 DB 조회)와 전용 검색 오케스트레이션(BGE-M3+리랭커)은 재현하지 않았다 — 검색기는 여기서도 ours와 동일한 임베딩을 쓴다. 원 논문 본문은 "1000토큰, 겹침 200토큰"이라 적지만 원 논문이 공개한 코드는 글자 수(character) 기준으로 나눈다 — 코드 쪽을 따라 구현했고 그 불일치를 그대로 남겨둠(`scripts/retrieval_accuracy.py: trag_hetero_chunks` 주석).

⁵ **2026-09-20, `PREREG-2026-09-20-mt2net-reranker-hitab.md`**: MT2Net(Zhao 2022)의 실제 채점 메커니즘(질문+후보 문장 concat → BERT류 pairwise 분류기, `BAAI/bge-reranker-base` 기반)을 HiTab train split(7,388개 질의, 2,517개 표 — eval의 198개 표와 완전 분리, 코드 assert로 확인)에서 실제로 학습해 재현한 arm. `scripts/train_mt2net_reranker_hitab.py`, negative는 기성품 하이브리드 검색기(질의 자신의 표 안에서 상위 오답 7개)로 채굴. 평가는 `scripts/retrieval_accuracy.py --rerank-model`(신규 옵션, mt2net식 문장을 질의 자신의 표 안에서만 분류기 점수로 순위 매김 — 코퍼스 전체 스캔은 계산상 불가능하므로 제외).
**예측이 빗나감**: 사전등록은 "학습된 재정렬기가 mt2net식 템플릿(임베딩만)보다 낫거나 최소한 비슷"을 예측했으나, 실제로는 **더 나쁘다** — n=300 파일럿 0.9233(템플릿만 0.9500, ours 0.9667), 검정력이 큰 전체 test n=1581 기준으로는 0.8558(템플릿만 0.9386, ours 0.9418)로 McNemar p≈0(ours 대비, 템플릿만 대비 둘 다) — 유의한 **퇴보**다. 원인 미상(1 epoch 과소학습, negative 채굴 전략, 짧은 정형 문장에 대한 `bge-reranker-base`의 사전학습 편향 등 가능성이 있으나 상관관계 이상으로 기전을 단정하지 않음). §3(k=1/5/10/20 표)은 이번 작업 범위 밖 — 단일 운영점(budget=20)만 측정했다. 학습 로그·모델: `models/mt2net-reranker-hitab/`, `results/mt2net_reranker_hitab/`.

## 2. MultiHiertt 8-arm (train split, 예산=20, 문서 범위, 2908건)

| 검색 방법 | 단일조회 (m=1) | 다중조회 (m≥2) | 단일산술 (m=1) | 다중산술 (m≥2) |
|---|---:|---:|---:|---:|
| cell (ours) | 0.9479 | 0.8630 | 0.9577 | 0.8215 |
| mt2net_desc² (원문 후보 문장, 자체 검색기) | 0.9573 | 0.8795 | 0.9577 | 0.8359 |
| rowcol | 0.8673 | 0.8000 | 0.9296 | 0.7329 |
| trag_hetero⁴ | 0.8009 | 0.7534 | 0.8451 | 0.6713 |
| chunk | 0.8389 | 0.8000 | 0.8310 | 0.6875 |
| tablerag-path³ | 0.5687 | 0.3205 | 0.6338 | 0.3125 |
| tablerag-leaf³ | 0.4550 | 0.2521 | 0.6479 | 0.3062 |
| randrow | 0.1659 | 0.1068 | 0.2535 | 0.0989 |

- mt2net_desc가 네 지표 전부에서 ours를 근소하게 앞섬 — HiTab에선 없던 패턴.
- "다중조회/다중산술(m≥2) 비교" 착시 주의: 단순히 다중조회 acc와 다중산술 acc를 비교하면 산술이 더 쉬워 보이지만, m(정답 셀 개수)이 난이도의 주 요인이라 착시. m을 맞춰 비교(m=1끼리, m≥2끼리)하면 8개 arm 중 7개에서 단일/다중조회 ≥ 단일/다중산술 — 산술이 일반적으로 더 쉬운 게 아님.
- tablerag-leaf만 유일하게 반대(다중조회 .2521 < 다중산술 .3062). 원인 조사했으나 미해결: 숫자열 min/max 접힘 가설은 해당 케이스가 2224건 중 5건뿐이라 격차(~590건) 설명 못 함. Fisher 정확검정 p=0.036(미보정) — 8개 arm 동시검정 보정하면 못 버팀. 메커니즘 미상으로 보류.

² **2026-09-20 캐비엇**: 후보 문장은 MultiHiertt 데이터셋이 준 원문 `table_description`(MT2Net 저자 측 산출물)을 그대로 써서 이 부분은 추정이 아니다. 그러나 검색 메커니즘은 ours와 동일한 임베딩+하이브리드 유사도(코퍼스 전체 대상)이며, **아무것도 학습되지 않았다** — MT2Net 논문의 BERT pairwise 분류기(문서 내부 탐색)는 재현하지 않음. 이전 버전에 있던 "학습된 베이스라인"/"학습 기반" 표기는 오기이며 삭제함.
