# 지표 판정 — `all-covered@k` 는 질의 종류를 가로질러 비교할 수 없다 (2026-09-07)

**사후 분석.** 사전등록 없이, 이미 저장된 순위 덤프(`*_ranks.jsonl`)만 다시 읽어 만들었다. 검색 재실행도
재학습도 없다. 계측기 `analysis/stage1_board.py`. 사용자 질문에서 출발했다: *"표 검색이 잘 되는데 셀 검색은
잘 안 되고 있는 게 말이 안 되는 것 같다."*

## 한 줄 요약

**맞다. `all-covered@k` 는 k 를 셀 수로 고정하는데 요구량 m 은 질의마다 1~12 로 다르다. 조회와 산술을 같은
k 로 비교한 것은 다른 시험의 점수를 나란히 적은 것이고, 요구 셀당 같은 여유를 주면 test 산술은 .827 이 아니라
.922 다. 다만 이것은 자를 바꾼 값이지 검색기가 좋아진 값이 아니다.**

## 1. 무엇이 잘못됐나

`all-covered@k` = 상위 k 셀의 합집합이 gold 셀을 전부 덮으면 1.

- 조회형은 gold 셀이 **1개**다 → k=10 은 헛다리 9개를 봐준다.
- 산술형은 gold 셀이 **최대 12개**다 → k=10 은 헛다리를 −2개 봐준다. **정의상 불가능하다.**

각 k 에서 `m>k` 라 어떤 검색기로도 0 인 건수 (p1, 감사 통과 모집단):

| 모집단 | n | @1 | @3 | @5 | @10 | @20 |
|---|---:|---:|---:|---:|---:|---:|
| dev `corpus_arith` | 167 | **132** | 20 | 13 | 5 | 0 |
| dev `lookup_multi` | 31 | **31** | 3 | 0 | 0 | 0 |
| test `corpus_arith` | 179 | **127** | 10 | 7 | 1 | 0 |
| test `lookup_multi` | 29 | **29** | 0 | 0 | 0 | 0 |
| dev/test `lookup_all` | 809/727 | 0 | 0 | 0 | 0 | 0 |

`BOARD.md` 의 `셀|표@1 = .1677`(dev 산술)은 검색기를 재고 있지 않다 — 167건 중 132건(79%)이 정의상 0 인
칸이다. `lookup_multi` 의 `@1` 은 m≥2 뿐이므로 **항상 정확히 0** 이다. **@1·@3 열은 조회형에만 의미가 있다.**

## 2. 격차의 절반은 채점 방식이었다

`전체@10` 을 m 으로 층화하면 (같은 지표, 쪼개기만 함):

| 모집단 | m=1 | m=2 | m≥3 |
|---|---:|---:|---:|
| dev `corpus_arith` | **.9429** (35) | .6979 (96) | .1944 (36) |
| dev `lookup_all` | .9481 (809) | — | — |
| test `corpus_arith` | **.9038** (52) | .8421 (114) | .3846 (13) |
| test `lookup_all` | .9409 (727) | — | — |

**산술 m=1 은 조회와 사실상 같다** (dev .9429 vs .9481, test .9038 vs .9409). 셀 검색이 산술에서 못하는 것이
아니라, 산술 질의가 셀을 더 많이 요구하는데 예산을 안 늘려준 것이다.

같은 이유로 **dev .641 vs test .827 은 검색기 차이가 아니다** — dev 는 m≥7 이 13건, test 는 3건이다.

## 3. 교정: `all-covered@(c·m)` — 요구 셀당 c 칸

예산을 요구량에 비례시킨다. 인코더 p1, 감사 통과 모집단:

| 모집단 | n | m 최대 | c=1 | c=3 | c=5 | **c=10** | (참고) 전체@10 |
|---|---:|---:|---:|---:|---:|---:|---:|
| dev `corpus_arith` | 167 | 12 | .2994 | .5389 | .7126 | **.7665** | .6407 |
| dev `lookup_all` | 809 | 1 | .6959 | .8591 | .9197 | **.9481** | .9481 |
| dev `lookup_multi` | 31 | 5 | .3226 | .7742 | .8387 | **.8710** | .8065 |
| test `corpus_arith` | 179 | 11 | .4581 | .7709 | .8492 | **.9218** | .8268 |
| test `lookup_all` | 727 | 1 | .7043 | .8721 | .9161 | **.9409** | .9409 |
| test `lookup_multi` | 29 | 3 | .3448 | .8621 | .8966 | **.9655** | .8966 |

**c=10 을 고른 이유는 결과가 아니라 연속성이다.** 조회는 m=1 이므로 c=10 이면 k=10 과 정의상 같은 값이고,
표에서 `.9481 = .9481`, `.9409 = .9409` 로 확인된다. **사전등록된 조회 숫자를 하나도 바꾸지 않는 유일한 c 다.**
산술에만 유리하게 맞춘 상수가 아니라는 논거가 이것이다. c≥1 에서는 불가능한 질의가 없으므로 §1 의 문제도
같이 사라진다.

교정 후에도 산술은 조회보다 낮다 (dev .7665 vs .9481). **남은 .18 이 진짜 산술 열세다** (교정 전 .31).

### ⚠️ 이 지표의 한계 — 오라클 예산이다 (2026-09-07 추가)

**예산 `k = c·m` 을 정하려면 `m` 을 알아야 하는데 `m` 은 gold 셀 개수다.** 배포된 시스템은 질문만 보고
정답이 몇 개인지 모른다. 따라서 `@(c·m)` 은 **오라클이 예산을 정해주는 지표**이고, `셀|표@k` 가 표를
맞혔다고 가정하는 것과 같은 종류의 오라클이다. 인용할 때 반드시 함께 적을 것.

따라오는 제약 세 가지:

1. **배포 성능이 아니다.** 검색기의 *순위 능력*을 질의 종류 간에 공정하게 비교하는 용도로만 쓴다.
   "이 시스템이 산술에서 .92 를 낸다"는 문장은 이 지표로 쓸 수 없다.
2. **`c=10` 의 근거는 연속성 하나뿐이다.** 조회(m=1)에서 @10 과 같아 사전등록 숫자를 안 바꾼다는 것이
   전부이고, c 를 정당화하지 원리를 정당화하지 않는다. c=3 이면 산술 dev .5389 / test .7709,
   c=5 면 .7126 / .8492 다. 상수를 바꾸면 결론의 크기가 바뀐다.
3. **답변 성능의 대리 지표로는 `@10` 보다 나쁘다.** `@10` test 산술 .8268 일 때 같은 조건 답변 EM 은
   .29 였다 (§19/E4). `@(c·m)` 로 .9218 이 되어도 답변은 그대로다 — 리더는 고정 문맥 예산을 쓰므로
   m 에 비례해 문맥을 늘려주는 조건 자체가 실제 동작이 아니다. 검색 지표와 답변 지표를 잇는 다리로
   쓰지 말 것.

즉 **`@(c·m)` 은 "왜 산술 점수가 낮은가"를 설명하는 진단 지표이지, 성능을 주장하는 지표가 아니다.**
성능 주장은 `all-covered@10`(사전등록, 고정 예산, 오라클 없음)으로 한다.

## 5. 사전등록에 대한 입장 (중요)

- **`PREREG-2026-09-06-cell90.md` 의 주지표는 `all-covered@10` 그대로다.** 산술 목표 .9 에 대한 판정은
  **test .8268 / dev .6407 — 미달**로 남는다. 이 문장은 바뀌지 않는다.
- `@(c·m)` 로 test 산술이 .9218 이라는 것은 **사후 발견**이다. "목표 .9 달성"이라고 쓸 수 없다. 결과를 보고
  자를 바꾼 것이기 때문이다 (`PREREG-2026-09-07-scope-index.md`: *"결과를 보고 규칙을 바꾸지 않는다"*).
- 이 지표를 **주지표로 쓰려면 다음 실험의 사전등록에 먼저 적고 그 다음에 돌린다.**
- 논문에는 "이 지표는 질의 종류 간 비교에 부당하다"는 **방법론 관찰**로 쓸 수 있다. 이 주장은 결과와 무관하게
  참이다 (12개를 10칸에 넣을 수 없다는 것은 데이터를 보기 전에도 참이다).
