# 사전등록 v2: 셀 ID 선택 + 코드 값 반환 (2026-09-10)

`PREREG-2026-09-10-cell-id-selection.md`(v1)를 대체한다. v1 실행은 **장치 결함**으로
판정한다. 사후 취소가 아니라 v1 자신이 적어 둔 중단 조건이 발동한 것이다:
"형식 파손율 > 5% 이면 장치 결함으로 판정하고 EM 개선을 주장하지 않는다."
실측 파손율 17.0%. v1 의 EM 0.5943 은 어떤 결론에도 쓰지 않는다.

## v1 결함 두 개 (코드로 확인)

1. **ID 파서.** v1 은 `#\s*(\d+)` 만 인식했다. 리더는 지시대로 셀을 골랐지만
   `[#12]` 가 아니라 `[12]` 로 썼다 — no_id 249건 중 **194건이 이 형태**다.
   지시를 따른 출력이 버려졌다. (3건 맨숫자, 13건 값 직접 출력, 39건 진짜 기권.)
2. **ID→값 사전.** v1 은 문장→`VisibleCell` 사전이 문장 분해가 유일할 때만 값을
   돌려주었고, 동결된 문맥 31,620줄 중 128줄은 현행 코드가 더 이상 같은 문장을
   렌더하지 않아(표 제목 매핑이 그 뒤 바뀌었다) 해석 불가였다 → unresolved 20건.

## 장치 (v2)

- 문맥: 동결된 20줄에 `[#n]` 만 앞에 붙인다. 재검색·재색인·예산 변경 없음.
  `audit` 이 20줄 전부 `f"[#{k}] {원문}"` 과 바이트 동일함을 실행 전에 확인한다.
- 값 반환: 독립적인 두 경로를 두고 **서로 검증한 뒤** 쓴다.
  - 권위 경로: 코퍼스 셀을 재렌더해 문장→`table.data[i][j]` 로 사전을 만든다.
    값이 파서를 통과하지 않는다.
  - 문법 경로: 동결 문장에서 템플릿 문법으로 값을 읽는다. 값은 **마지막 " is "
    뒤, 끝 마침표 앞**이라 제목·헤더 속 숫자가 값으로 뽑힐 수 없다.
  - 실측: 두 경로가 말이 겹치는 줄 전부에서 일치 — test 31,492/31,492,
    dev 33,380/33,380, 불일치 0. 권위 경로에 없는 128줄만 문법 경로로 채운다.
    (`results/cell_id_v2/AUDIT_{test,dev}.json`)
- 단위·접미사·괄호를 떼거나 비율을 바꾸지 않는다. 셀에 저장된 문자열 그대로.
- 추가 셀·추가 의미 정보를 넣지 않는다.

## 파싱·오류 처리 규칙 (실행 전 고정, 세 후보는 dev 가 고른다)

    hash          `#\s*(\d+)`                     — v1 규칙, 재현용으로만 보존
    bracket       `[#n]` `[n]` `#n` 합집합, 등장 순 중복 제거
    bracket_bare  bracket, 없고 출력 전체가 정수 목록이면 그 정수들

- 복수 ID: 등장 순서대로 값을 `", "` 로 잇는다 (BASE 가 복수 값에 쉼표를 쓰는 규칙).
  gold `m` 을 보고 단일 선택을 강제하지 않는다 — 개수는 질문과 출력만으로 정한다.
- 범위 밖 ID: 버린다. 남은 값이 없으면 예측은 빈 문자열이고 **오답으로 채점**한다.
- 해석 불가 ID: 같다. 빈 문자열, 오답.
- ID 가 하나도 없으면(기권 포함) 빈 문자열, 오답.
- **어떤 문항도 분모에서 빼지 않는다.** 파손율을 EM 과 함께 보고한다.
- 모델이 값을 직접 쓰면 그 값을 쓰지 않는다 (bracket_bare 의 정수 목록 예외만).

## dev 에서 고르는 것 (test 를 보고 고르지 않는다)

- 모집단: HiTab **dev** 분할을 같은 검색 설정으로 새로 돌렸다
  (`cell_id --split dev --corpus split --unit cell --template s3c --alpha 0.7
  --budget 20`), 1,669 채점, 주지표형 1,062. 리포의 "dev 없음"(CLAUDE.md §0.4)은
  사용자 지시로 이 실험에 한해 해제한다 — 프롬프트·파싱 규칙을 test 에서 고르지
  않기 위해서다. dev 수치는 **선택용이며 성능 주장에 쓰지 않는다.**
- 비용 때문에 dev 앞 700문항(파일 순서, 고정)만 쓴다.
- 프롬프트 후보 둘: `p1`(v1 문구 그대로), `p2`(p1 + 형식 예시 한 줄).
- **선택 규칙: dev 주지표 EM 이 가장 높은 (프롬프트, 파싱규칙) 조합.** 동점이면
  파손율이 낮은 쪽, 그래도 동점이면 `p1`, `bracket`. 파싱 규칙 셋은 같은 생성물에서
  오프라인으로 채점하므로 추가 생성 없음.
- dev BASE(자유 생성)도 같은 700문항에서 돌려 dev 델타를 본다.

## 예측 (실행 전 고정)

- 주예측: **test 주지표 EM 0.74, 예상 범위 [0.68, 0.80].** 근거: v1 에서 선택
  자체는 작동했고(파손 제외분 1,312건) 파손 194건 회수가 그만큼 더해지지만,
  sparse 실험에서 개입 하나가 149건을 뒤집고 순 +11만 남긴 전례가 있어
  덧셈 가정을 하지 않는다.
- 목표 0.8(793/991)은 사용자 목표다. **미달이면 미달로 보고한다.**
- 장치 절대 상한(완벽한 선택기가 문맥 셀 값을 그대로 반환): 이번 실행 후
  gold 로 사후 계산해 함께 보고한다. 사전 계산치는 894/991 = 0.9021 (v1).

## 판정

- 지지 조건: **주지표 Δ ≥ .02 AND paired exact McNemar p < .05.** 둘 다.
- 95% paired bootstrap CI (B=10,000, seed=42) 함께 보고.
- 중단 조건: **형식 파손율 > 5%** — 넘으면 다시 장치 결함이고 EM 개선을 주장하지
  않는다. EM 보다 먼저 본다.
- test 는 **한 번만** 돌린다. 결과를 보고 프롬프트·파싱 규칙을 바꾸어 재시도하지
  않는다. 개별 문항에 맞춘 예외 규칙을 넣지 않는다.
- 이 test 는 이미 여러 번 분석되었다. 독립 신규 test 성능으로 주장하지 않는다.
- oracle(정답을 보고 실행 중 고르기) 수치를 EM 으로 보고하지 않는다.
