# 사전 등록 — HiTab test split 확인 런 (2026-08-24)

**결과를 보기 전에 커밋한다.** `PREREG-2026-08-23-compact-untitled.md`의 후속이다.

## 왜 하는가 — 이 저장소의 모든 설계 선택이 dev에서 이뤄졌다

색인 단위(S3), 제목 조항(S3c), 예산(512·1024), 검색기(dense), 인코더, 리더,
모집단 정의까지 전부 **HiTab dev**에서 골랐다. `RESEARCH_STRUCTURE.md` §3.1이
"test split은 미소진, 최종 보고용으로 보존"이라고 못박아 뒀고, 지금까지 지켰다.

리뷰어가 가장 먼저 찌를 자리가 여기다. **한 번도 안 만진 split에서 같은 부호와
같은 크기가 나오면 그 지적이 통째로 사라진다.** 나오지 않으면 그것도 사실대로 적는다.

**이 런은 튜닝이 아니다.** 손잡이를 하나도 돌리지 않는다. dev에서 확정된 설정을
그대로 복사해 다른 split에 붙일 뿐이고, 아래 예측은 **dev 수치를 그대로 옮긴 것**이다.

## test split은 dev와 구조적으로 같은가 — LLM 없이 먼저 쟀다 (2026-08-24)

예측을 세우려면 두 코퍼스가 같은 물건인지부터 알아야 한다. **답을 한 건도 보지 않고**
셀 수준 통계만 전수로 쟀다. 스크립트는 `scripts/cell_sentence_collision.py`의
`render`/`collisions`를 그대로 쓰고, 토큰은 `BAAI/bge-small-en-v1.5` 토크나이저다.

| | dev | **test** | 차이 |
|---|---|---|---|
| 표 | 424 | **414** | −10 |
| 셀 | 58,759 | **58,460** | −299 |
| 조회형 질의(모집단) | 830 | **769** | −61 |
| **제목 보유** | 99.29% | **99.03%** | −0.26점 |
| S3 셀당 토큰 | 38.2 | **37.7** | −0.5 |
| MT2Net 셀당 토큰 | 16.9 | **16.5** | −0.4 |
| S2 셀당 토큰 | 15.9 | **15.5** | −0.4 |
| flat 주소 충돌 | 84.54% | **81.74%** | −2.8점 |
| S2 주소 충돌 | 13.12% | **14.52%** | +1.4점 |
| **S3 주소 충돌** | 9.14% | **10.17%** | +1.0점 |
| S3 표 넘는 충돌 | 7.31% | **7.28%** | −0.03점 |

**두 코퍼스는 같은 물건이다.** §충돌률 절의 예측자(주소 충돌)와 §용량-정밀도의
예측자(토큰 길이비 S3:MT2Net = 2.26배 dev / **2.29배 test**)가 전부 같은 구간이다.
제목 보유율도 99%대로 같으므로 **S3c는 test에서도 사실상 S3와 같다.**

→ 따라서 **예측은 "dev와 같은 수를 낸다"이고, 크기 구간까지 dev 값에서 옮긴다.**
S3 주소 충돌이 1.0점 높으므로 절대값은 아주 조금 낮을 수 있다.

## 무엇을 고정했는가 (실행 전)

모집단 `populations/hitab_test_lookup_all.txt`, n=769.
`scripts/freeze_populations.py::hitab_test_lookup_all` — `hitab_dev_lookup_all`과
**같은 필터·같은 seed-0 순서·풀 전체**다. `build_population`은 dev만 pin하므로
test는 unset 우회 없이 그대로 파생된다. **이 문서와 함께 커밋한 뒤 다시 만들지 않는다.**

| 항목 | 값 |
|---|---|
| 코퍼스 | HiTab **test** split (표 414 / 셀 58,460) |
| 모집단 | `hitab_test_lookup_all`, n=769 |
| 예산 | 512 (주) / 1024 (부차) |
| 검색기 | dense (`BAAI/bge-small-en-v1.5`) |
| 리더 | `local:Qwen/Qwen2.5-7B-Instruct?quantization=4bit&dtype=float16` — **네 런 전부 동일** |
| 채점 | `hitab_exact_match_text` |
| 우리 arm | `--cell-scheme S3c` (방법의 확정 정의) |
| 대조 | `--cell-scheme mt2net` (발표된 색인 단위) |
| 검정 | exact McNemar, `scripts/paired_em_between_runs.py` |
| 보정 | **P1·P2·P4a·P4b·P4c 5건에 Holm** (P3·P5·P6·P7은 기술 통계·통제로 보정 밖) |

**리더 스펙을 네 런에서 통일하는 이유**: dev에서 `h2h830_*`는 bfloat16 기본값이고
`s3c_*`는 4bit라 두 계열을 가로질러 짝지으면 리더 교란이 섞인다(§R3의 통제가 실제로
그걸 잡아냈다). test 런은 **자기 안에서 완결**되도록 네 런의 리더를 하나로 맞춘다.

## 예측

### P1 (주) — 512에서 우리가 MT2Net을 이긴다

dev 512: **.604 대 .518, +.086** (S3 기준 +.082, Holm p=3.11e-05).

**예측: 차이 +.04 ~ +.12, 부호 양, McNemar Holm 보정 후 p < .01.**

### P2 (주) — 1024에서도 같은 방향이고, 더 크다

dev 1024: **.599 대 .479, +.120** (Holm p=1.04e-09).

**예측: 차이 +.06 ~ +.16, 부호 양, Holm 보정 후 p < .01.**
그리고 **P2의 차이 > P1의 차이**(dev에서 +.120 > +.082였던 것과 같은 순서).

### P3 (절대값) — 두 arm의 EM이 dev 구간에 앉는다

| arm | 예산 | dev | **test 예측 구간** |
|---|---|---|---|
| 우리(S3c) | 512 | .604 | **.55 ~ .65** |
| MT2Net | 512 | .518 | **.47 ~ .57** |
| 우리(S3c) | 1024 | .604(=S3 .599) | **.55 ~ .65** |
| MT2Net | 1024 | .479 | **.42 ~ .53** |
| flat | 512 | .160 | **.12 ~ .21** |

### P4 (검색 단위 주장) — 512에서 cell이 셋을 다 이긴다

dev 512 (`corpus_dump_vs_cell_s3_dense_512`, n=100 계열)와 §코퍼스 규모 정면대결 기준.

* **P4a — cell > dump**, 차이 ≥ +.20, Holm 후 p < .001.
  (§"셀 단위 > 표 덤프"가 4/4"가 5/5가 되는지. 이 주장만 세 데이터셋에서 깨끗했다.)
* **P4b — cell > row**, 차이 ≥ +.15, Holm 후 p < .001.
  (AIT-QA에서 `row`가 우리를 이겼다. **HiTab test에서도 row가 이기면 검색 단위 주장은
  데이터셋 하나가 아니라 split 하나에서도 흔들리는 것**이므로 크게 다시 쓴다.)
* **P4c — cell > flat**, 차이 ≥ +.30, Holm 후 p < .0001.
  (경로 주장. 세 데이터셋 전부에서 살아 있는 유일한 주장이고, 여기서 깨지면 논문이 없다.)

### P5 (메커니즘) — MT2Net은 예산을 키우면 나빠지고 우리는 평평하다

dev: MT2Net .518 → .479(**−.039**), 우리 .600 → .599(**−.001**).

**예측: MT2Net 1024 < MT2Net 512 (부호 음), 우리 |Δ| ≤ .03.**
§문맥 크기 최적점의 곡선이 **짧은 문장 쪽에서 더 가파르다**는 관찰의 재시험이다.

### P6 (유효성 통제) — flat arm이 같은 예산의 두 런에서 0:0

`flat`은 `--cell-scheme`을 읽지 않는다. **512의 두 런, 1024의 두 런에서 각각
EM이 소수점까지 같고 불일치 쌍이 0:0이어야 한다.**

**0:0이 아니면 셀 템플릿 말고 다른 것이 움직인 것이므로, P1~P5를 해석하기 전에
원인부터 찾는다.** 2026-08-24에 이 검사가 리더 교란을 잡아낸 전례가 있다.

### P7 (OSC는 판정에 쓰지 않는다) — 그래도 기록한다

**예측: OSC는 두 예산 모두 MT2Net이 높다**(dev 512 .813 대 .788, 1024 .863 대 .849).
문장이 2.29배 길어 같은 예산에 덜 담기기 때문이다. **그것으로 채택하지 않는다.**
OSC로 골랐으면 dev에서 .082를 버렸을 것이라는 §판정 기준의 재확인이다.

문맥에 들어온 표 수도 기록한다 (dev 512: 우리 2.41 대 저쪽 6.06).

## 무엇이 예측을 깨는가 — 처리를 미리 정한다

| 관측 | 함의와 처리 |
|---|---|
| **P1의 부호가 음** | 헤드라인 주장이 dev 전용이다. §발표된 색인 단위 절을 **"dev에서 성립하고 test에서 재현되지 않았다"**로 다시 쓴다. 숨기지 않는다 |
| **P1이 양이지만 유의하지 않음** | "이긴다"를 못 쓴다. n=769는 dev n=830과 거의 같으므로 **검정력 부족으로 변명할 수 없다** — dev에서 151:83이었던 것이 test에서 무승부면 그것이 결과다 |
| P1이 예측 구간(+.04~+.12) 밖으로 크게 양 | **예측 실패로 적는다.** 부호가 맞아도 크기를 못 맞춘 것이다 |
| **P4b가 깨짐 (row > cell)** | 검색 단위 주장이 HiTab 안에서도 흔들린다. AIT-QA의 ❌와 합쳐 **"검색 단위 주장은 코퍼스 의존"**을 훨씬 강하게 쓴다 |
| **P4c가 깨짐 (flat ≥ cell)** | 논문의 중심 주장이 무너진다. 다른 결과 해석을 전부 멈추고 이것부터 본다 |
| **P6이 깨짐 (flat이 0:0 아님)** | 런 전체를 폐기하고 리더·환경부터 맞춘다. 결과가 아니라 안전장치다 |
| P5가 깨짐 (MT2Net이 1024에서 오름) | §문맥 크기 최적점의 "짧은 문장이 더 가파르다"가 dev 전용 관찰이 된다. 기각이 아니라 조건부로 강등 |

## 이 런이 하지 않는 것

* **test로 무엇도 고르지 않는다.** 어떤 결과가 나오든 손잡이를 다시 돌려 test를
  다시 돌리지 않는다. 그 순간 test는 두 번째 dev가 된다.
* **다른 데이터셋을 건드리지 않는다.** RealHiTBench·AIT-QA·MultiHiertt는 그대로 둔다.
* **어순(leaf-first) 몫 분리(남은 일 2번)를 여기서 섞지 않는다.** 별도 사전 등록이다.

## 실행 (이 문서 커밋 후)

공통: `--dataset hitab --split test --population hitab_test_lookup_all
--retriever dense --reader 'local:Qwen/Qwen2.5-7B-Instruct?quantization=4bit&dtype=float16'`

```
--cell-scheme S3c    --budget 512  --arms flat,cell,dump,row  --out results/test_s3c_512.json
--cell-scheme mt2net --budget 512  --arms flat,cell           --out results/test_mt2net_512.json
--cell-scheme S3c    --budget 1024 --arms flat,cell           --out results/test_s3c_1024.json
--cell-scheme mt2net --budget 1024 --arms flat,cell           --out results/test_mt2net_1024.json
```

`dump`/`row`는 `--cell-scheme`을 읽지 않으므로 512에서 한 번만 낸다.
짝지음은 `scripts/paired_em_between_runs.py`로 `*_records.jsonl` 사이에서 한다.
