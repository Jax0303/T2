# 사전 등록 — RealHiTBench 수치추론 전수, 큰 표에서 검색이 표-제공을 이기는가

**결과를 보기 전에 커밋한다.** 저장소 규칙: 예측을 숫자로 박고 실행하며,
결과를 보고 규칙을 고르지 않는다.

## 0. 왜 이 실험인가 — 프레임

지금까지의 답변 정확도는 전부 **단일 셀 조회(m=1)** 모집단에서 나왔다. 이유는 연구
설계가 아니라 리더 제약이다 — 산술 모집단에서 로컬 4-bit 7B는 전 arm EM .011~.086이라
arm을 가르지 못한다(`RESULTS.md` §산술 모집단에는 로컬 7B를 쓰지 말 것).

그런데 **그 벽은 우리만의 것이 아니다.** RealHiTBench 원논문(arXiv:2506.13405, Table 2)이
**같은 모델(Qwen2.5-7B-Instruct)에 표를 통째로 주고** 수치추론 EM **5.32**를 보고한다.
같은 모델의 Fact Checking 18.65 / Structure 23.48과 대조하면, 못 하는 것은 계층 표 독해가
아니라 **산술**이다.

⚠️ **단, 그 벽은 "7B의 벽"이 아니라 "범용 7B의 벽"이다.** 같은 표에서 **TableGPT2-7B가
NR EM 29.31**, TableLLM-Qwen2-7B가 **22.05**를 낸다 — 파라미터 수가 같은데 표 특화
사후학습만으로 5.5배다. 그래서 이 사전등록은 리더를 **둘** 건다(§1). 약한 리더에서만
성립하는 주장은 "리더가 나빠서 그렇다"로 반박당하기 때문이다.

그러면 질문이 바뀐다. "리더가 산술을 못 하니 조회형만 한다"가 아니라,
**"리더가 산술을 못 하는 조건에서, 표를 통째로 주는 것과 검색해서 셀만 주는 것 중
무엇이 나은가"**이다. 그리고 RealHiTBench는 그 질문에 이상적인 무대다 —
gold 표 중앙값이 **1,561토큰**이고 **86%가 512 예산을 넘는다**(최대 12,477).

**주장하려는 것:** 표가 리더의 유효 독해 용량을 넘으면, 검색으로 뽑은 셀 몇 줄이
표 전체보다 낫다. 이것이 참이면 "표가 주어지므로 검색이 불필요하다"는 반박이
**표 크기 조건부로** 무너진다.

**이미 가진 방증** (`results/rhb_dense_512_s3_casefix_records.jsonl`, n=243):

| gold 표 크기 | n | cell (검색, 512tok) | dump (표 단위 색인) |
|---|---|---|---|
| ≤512 | 35 | .200 | **.257** |
| 513–2048 | 131 | **.183** | .015 |
| 2049–8192 | 68 | **.250** | .015 |

⚠️ `dump`의 .015는 공정한 대조가 아니다 — `corpus_dump_vs_cell.py`의 dump arm은
예산을 넘는 표를 **자르지 않고 건너뛴다**. 그래서 이 실험은 `goldtable` arm을 새로 만든다.

## 1. 설정

| | |
|---|---|
| 데이터셋 | RealHiTBench, `QuestionType == "Numerical Reasoning"` **771건 전수** |
| 모집단 | `rhb_nr_all` (새로 동결). **EM 전용** — gold 셀 주석 불필요 |
| 리더 A (약함) | `local:Qwen/Qwen2.5-7B-Instruct?quantization=4bit&dtype=float16` — 발표 NR **5.32** |
| 리더 B (표 특화) | `local:tablegpt/TableGPT2-7B?quantization=4bit&dtype=float16` — 발표 NR **29.31** |
| 검색기 | **dense**, 셀 스킴 `S3c` |

⚠️ 저장소 기본 검색기는 2026-08-27에 `hybrid α=0.7`로 바뀌었다(`CLAUDE.md`). **이 실험은
의도적으로 dense를 쓴다** — P1·P2의 예측 구간이 dense 런(`rhb_dense_512_s3_casefix`)에서
유도됐으므로, 검색기를 같이 바꾸면 예측이 근거를 잃는다. hybrid 확인은 별도 런으로 뒤에 붙인다.
| 예산 | 512 (주) · 1024 (부) |
| 채점 | `hitab_exact_match_text` (전 arm 동일) |

### arm

| arm | 내용 |
|---|---|
| `cell` | 코퍼스 전체 셀 색인 → 예산까지 채움 (**본 방법**) |
| `goldtable` | **gold 표를 예산 무시하고 통째로** = RealHiTBench 논문의 조건을 우리 리더로 재현 |
| `flat` | 잎 라벨만 (통제) |

**`goldtable`이 이 실험의 핵심이다.** 발표된 5.32와 직접 비교하면 모집단·채점기·양자화가
동시에 다르다. `goldtable`은 같은 질의·같은 채점기·같은 4-bit 리더이므로 **남는 차이가
"검색이냐 표-제공이냐" 하나**가 된다.

## 2. 왜 OSC를 안 재는가

RealHiTBench 수치추론의 답은 대개 **계산 결과**라 표의 어느 셀에도 없다. 기존 모집단
`rhb_lookup_all`은 "답 문자열이 셀 값과 일치"를 요구했고, 그래서 NR 771건 중 **55건(7.1%)**
만 남았다 — 그것도 각 하위유형 안에서 **답이 이미 표에 적혀 있는 쉬운 인스턴스**들이다.

| NR 하위유형 | 전체 | 기존 모집단 | 생존률 |
|---|---|---|---|
| Calculation | 256 | 17 | 6.6% |
| Counting | 205 | 18 | 8.8% |
| Comparison | 127 | 6 | 4.7% |
| Ranking | 105 | 12 | 11.4% |
| Multi-hop NR | 78 | 2 | 2.6% |

그 필터는 **OSC를 재기 위해** 있었다. EM에는 필요 없다. 그래서 이 실험은 필터를 걷고
**OSC를 포기한다.** 기전 설명은 OSC 대신 `문맥의 표 수` · `tokens` · `gold 표 크기`로 한다.

## 3. 예측 (숫자로 커밋한다)

| ID | 예측 | 구간 |
|---|---|---|
| **P1 (주)** | gold 표 **>2048토큰** 구간에서 `cell` − `goldtable` | **≥ +.05** |
| **P2 (주)** | gold 표 **≤512토큰** 구간에서 `goldtable` − `cell` | **≥ +.03** |
| **P3** | P1과 P2의 **부호가 반대** (교차점 존재) | 부호만 |
| **P4** | 771 전수 `cell` EM은 기존 55건의 .0909보다 **낮다** | **.03 ~ .08** |
| **P5** | `cell` > `flat` | ≥ +.03 |
| **P6 (통제)** | `flat` arm이 `cell`/`goldtable` 두 런에서 불일치 ≤5, p 유의하지 않음 | — |

| **P8 (범위)** | P1이 **두 리더 모두에서** 성립한다 | 부호만 |

### P8이 이 실험의 진짜 시험이다

약한 리더(A)에서만 P1이 서면, 주장은 **"약한 리더에서는 검색이 낫다"**로 좁아지고
"더 좋은 리더를 쓰면 될 일"이라는 반박에 그대로 노출된다. 표 특화 리더(B)는 같은 7B로
NR 29.31을 내므로 **표를 통째로 읽는 능력 자체가 A보다 훨씬 낫다** — 그런데도 큰 표에서
검색이 이기면, 주장은 리더 품질이 아니라 **문맥 길이의 성질**에 관한 것이 된다.

**B에서 P1이 깨지면 그렇게 적는다** — "이 이득은 리더가 표를 다 못 읽을 때만 존재한다"가
결론이고, 그것도 보고할 값이 있는 범위 조건이다.

### P7 — 발표 수치(5.32)와의 대조는 **불확실하다고 미리 적는다**

P4의 구간 .03~.08이 5.32를 **가로지른다.** 넘을 수도 못 넘을 수도 있다고 실행 전에
적어둔다. **넘으면 보고하고, 못 넘어도 P1이 서면 이 실험의 주장은 산다** — 주장은
"발표 수치를 이겼다"가 아니라 **"표가 크면 검색이 표-제공을 이긴다"**이기 때문이다.

사후에 "우리는 원래 P1을 노렸다"가 되지 않도록 **여기 미리 못박는다.**

## 4. 판정 규칙

- P1·P2가 둘 다 서면 → **프레임 확정.** 논문에 "표 크기 조건부로 검색이 표-제공을 이긴다"를 쓴다
- P1만 서고 P2가 안 서면 → 교차점 주장은 버리고 "큰 표에서 검색이 낫다"만 쓴다
- P1이 안 서면 → **프레임 폐기.** RealHiTBench 수치추론은 이 방법의 무대가 아니라고 적는다
- P6이 깨지면 → 다른 예측을 해석하지 않는다. 리더·환경 교란이므로 재실행
- **P8이 서면 → 주장은 리더 품질이 아니라 문맥 길이에 관한 것이다.** 이게 최선의 결과
- **P8이 깨지면 → "약한 리더 한정"으로 범위를 좁혀 적는다.** 숨기지 않는다
- 리더 B가 8GB에 안 올라가면(4-bit 실패) → A만으로 돌리고 **P8은 미측정으로 남긴다.**
  나중에 채운다고 적고, A 결과를 P8이 선 것처럼 서술하지 않는다

## 5. 이 실험이 답하지 않는 것

- **다중 피연산자(m≥2) 산술의 답변 정확도** — 여전히 HiTab 산술 레그(무료 API 한도)에 막혀 있다
- **OSC** — 위 §2
- **저쪽 논문 수치와의 직접 비교** — 채점기가 다르다. `goldtable`이 그 자리를 대신한다

## 6. 실행

```
# 1) 모집단 동결
PYTHONPATH=. .venv/bin/python scripts/freeze_populations.py --only rhb_nr_all
# 2) 본 실험
PYTHONPATH=. .venv/bin/python scripts/corpus_dump_vs_cell.py \
    --dataset realhitbench --population rhb_nr_all \
    --arms cell,goldtable,flat --cell-scheme S3c --retriever dense \
    --budget 512 --reader local:Qwen/Qwen2.5-7B-Instruct \
    --out results/rhbnr_s3c_512.json
# 3) 리더 B (표 특화) — 같은 모집단, 같은 arm, 리더만 교체
PYTHONPATH=. .venv/bin/python scripts/corpus_dump_vs_cell.py \
    --dataset realhitbench --population rhb_nr_all \
    --arms cell,goldtable,flat --cell-scheme S3c --retriever dense \
    --budget 512 --reader local:tablegpt/TableGPT2-7B \
    --out results/rhbnr_tgpt_512.json
```

## 7. 실행 전 확인 사항

- **로컬 사본이 공식 배포와 다르다.** 공식 RealHiTBench는 708표 / 3,752 QA인데
  `data/realhitbench/QA_final.json`은 **3,071 QA**이고 HTML이 있는 표가 **540개**다.
  어느 쪽을 썼는지 논문에 명시하고, 저쪽 수치와 나란히 놓을 때 단서를 단다.
- TableGPT2-7B가 8GB에 4-bit로 올라가는지 먼저 확인한다. 안 되면 위 판정 규칙대로.
