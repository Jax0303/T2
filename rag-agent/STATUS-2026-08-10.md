## 1. RealHiTBench 채점기 — 3건 수정, 4개 파일 재채점

### 왜

"다른 논문들은 널널하게 채점하니 우리도 맞추자"에서 출발했으나, **비교군을 두 번 잘못 잡았다.**

- 1차: RealHiTBench 자체 프로토콜을 봤다 → Numerical Reasoning은 **F1 + EM**(§5.1, 원문 확인).
  LLM judge는 Data Analysis 태스크 한정. 우리가 관행에서 벗어난 게 아니었다.
- 2차 (사용자 지적으로 교정): **경쟁 상대는 벤치마크가 아니라 table-RAG 방법 논문들**이고,
  거기는 LLM judge를 쓴다 — TableRAG(EMNLP 2025)는 *"assessed by Qwen-2.5-72B, binary 0 or 1"*.
  **그 기준으로는 우리 채점이 필드에서 가장 엄격하다.**

### 무엇을

| 수정 | 내용 | 영향 |
|---|---|---|
| ① half-up 반올림 | `round()`(은행가) → `ROUND_HALF_UP`. gold가 반올림된 형태로 쓰였으므로 채점기도 같은 방식이어야 함 | 판정 **1건** 뒤집힘 |
| ② 토큰 F1 추가 | 벤치마크가 EM과 **함께** 보고하는 지표 | 신규 |
| ③ 수치/텍스트 gold 층 분리 | `gold_is_numeric()` | 신규 |

③의 근거: 부분집합 필터가 gold가 `Japan` / `Crew C` / `2015-11-03, 2403` / `Decrease by 0.03.`
같은 질문 **16/94(17%)** 를 통과시켰는데, 솔버 프롬프트는 숫자만 요구한다. 구조적으로 답이 불가능.
**양쪽 arm 전부 0.0000, 불일치쌍 0** → 빼도 McNemar p가 **정확히 불변**이다. 정확도만 오른다.

### 결과 (claude-sonnet-5)

| 지표 | n | S1 | S2 | Δ | p |
|---|---|---|---|---|---|
| EM 전체 | 94 | .2128 | **.3085** | +.0957 | **.0352** |
| EM 수치 gold만 | 78 | .2564 | **.3718** | +.1154 | .0352 |
| 토큰 F1 | 94 | .2128 | .3138 | +.1011 | — |

gpt-4.1-mini / gpt-5.1 / llama70b는 판정 변동 **0건**(체계적 완화가 아니라는 증거). 수치는 `RESULTS.md` I절.

### ⚠️ 반드시 논문에 적을 것

**유의성이 판정 1건에 걸려 있다.** p가 .0574 → .0352로 내려간 것은 half-up 수정이 뒤집은
`4.125` vs gold `4.13` **한 건**의 결과다. 버그는 독립적으로 식별했고 테스트로 고정했지만,
이 유의성은 깨지기 쉽다.

### ❌ `numeric_match`(±2%) 인용 영구 금지

실측 확인: `37710.20` vs `38355.9`, `133,500` vs `131200`, `99` vs `100`을 전부 정답 처리.
`abs()`까지 허용해 부호 반전도 통과한다. 관대한 게 아니라 틀린 것.

## 2. 복원 — 세그먼트 F1 추가, 행 구조 분류

### 세그먼트 F1

완전일치는 하류에 맞는 지표지만(경로 한 조각만 틀려도 문장이 오염됨) TSR 문헌(TEDS/GriTS/
adjacency-F1)은 전부 부분 점수라, `.68`을 그쪽 눈금으로 읽으면 훨씬 나쁘게 보인다. 둘 다 낸다.

| 설정 | n | 열 exact / **F1** | 행 exact / **F1** |
|---|---|---|---|
| 경계 gold · dev | 424 | .9749 / **.9930** | .7607 / **.9279** |
| 경계 gold · test | 414 | .9709 / **.9931** | .7614 / **.9328** |
| 경계 추정 · train | 2,043 | .9175 / **.9717** | .6829 / **.8905** |
| 경계 추정 · test | 414 | .8839 / **.9595** | .6682 / **.8839** |

정의: 경로 세그먼트의 **다중집합 F1, 복원 vs gold**. 누락은 recall을, 다른 가지에서 새어든 것은
precision을 깎는다. `tree_reconstruct_multihiertt.py`의 `segment_coverage`와 **다른 것** —
그쪽은 gold 트리가 없어 셀 설명 문장과 대조하는 프록시다. 결과 파일에 note로 박아뒀다.

기존 exact_match 값은 **하나도 변하지 않았다**(F1 필드만 추가).

### 행 구조 분류 (신규 측정, 결과 파일 없음 — 재실행 필요)

HiTab dev+train 2,467표, 경계 추정 포함:

| 행 구조 | 표수 | 비중 | 표 완전복원 | 행 라인 |
|---|---|---|---|---|
| 평탄 — 계층 없음 | 322 | 13.1% | .929 | .940 |
| 계층이 스텁 열 안에 들어감 | 1,141 | 46.3% | .856 | .980 |
| 구획행형 — 제목 행에 값 없음 | 616 | 25.0% | .599 | .664 |
| **데이터 부모형 — 부모 행이 값도 가짐** | **388** | **15.7%** | **.000** | .206 |

**388표 중 완전복원 0표.** 부모 행이 자기 값을 가지면 자식 행과 그리드에서 구별이 불가능하다.

실패 822건의 원인 분해: **구조적 698(84.9%) / 경계 추정 124(15.1%)**.
경계 추정은 범인이 아니다(행 경계 정확도 .9481).

**산술적 천장 ≈ .83** — 표현 가능 247 + 구획행으로 복구 가능 106, ÷424.
논문에 `.76`만 쓰지 말고 **"천장 83% 중 .76"** 으로 쓸 것.

### 채점에서 빠지는 표

`unaligned` **592표** — gold를 그리드에 맞출 수 없어 어떤 수치에도 안 들어간다.
3,059표 중 19%. 논문에 제외율을 밝혀야 한다. **원인 미규명, 열린 과제.**

## 3. 들여쓰기 채널 — 부정, 짓지 말 것

가설: 계층 표현 채널은 유한하고, 우리가 `padding-left`/`nbsp` 들여쓰기를 버리고 있으니 켜면 이득.

**RealHiTBench 259표 전수 측정 결과 기각.** 행마다 **첫 번째 라벨 있는 칸**만 제대로 보면:

- 0 아닌 들여쓰기 보유: **8표 (3.1%)**
- 2단계 이상 = 실제 계층 신호: **4표 (1.5%)**

(초기에 20.1%로 잘못 쟀다 — 행 라벨이 아닌 칸의 `padding-left`를 셌고 정규식이 헐거웠다.)

HiTab은 더 확실하다: raw `texts` 1,500표 중 선행 공백이 남은 표 **0개 (0.0%)**.
export 시점에 이미 제거됐다. **데이터 부모형 388표는 알고리즘 문제가 아니라 정보 부재다.**

남은 후보는 RealHiTBench의 **LaTeX 원본**(`\hspace`/`\quad`) — HF 캐시에 미다운로드, 미확인.

## 4. TableRAG 비교 — 이식 완료, 헤드라인 비교는 차단

### 배경

"다른 table-RAG 논문 대비 +10%"가 목표. 그런데 **공통 지반이 없다**:

| 방법 논문 | 평가 데이터셋 |
|---|---|
| TableRAG (NeurIPS 2024) | ArcadeQA, BirdQA, WikiTableQuestions — 거대 **평면** 표 |
| TableRAG (EMNLP 2025) | HybridQA, WikiTableQuestion, HeteQA |
| T-RAG (2504.01346) | MultiTableQA — 자체 벤치마크 |
| HD-RAG (2504.09554) | DocRAGLib — 자체 데이터셋 |

**HiTab / MultiHiertt / RealHiTBench로 평가한 방법 논문이 없다.** 이것 자체가 연구 공백이지만,
공백에는 비교 대상도 없다.

### 이식한 것

`rag_agent/serialization/tablerag_unit.py` — TableRAG(NeurIPS 2024)의 `build_cell_corpus`
충실 이식. `tests/test_tablerag_unit.py` 5건이 형식을 고정.

TableRAG를 고른 이유: 얘도 **셀 단위 검색**을 해서, 차이가 "셀 인코딩에 계층 헤더 경로를
넣느냐"** 하나로 좁혀진다. 이론상 이상적인 대조군.

### 왜 차단됐나 (HiTab 800표 실측)

| | |
|---|---|
| 숫자 열 비율 | 77.1% |
| **숫자 셀 = 개별 색인 안 됨** | **76.4%** (74,884 / 98,045) |
| 색인 단위 ÷ 실제 셀 | **15.4%** |
| 개별 셀 doc이 0개인 표 | **68.4%** |

TableRAG는 숫자 열을 `{"column_name":…, "min":…, "max":…}` **요약 하나**로 접는다.
집계 질의의 피연산자는 전부 숫자 셀이므로, OSC로 재면 **0 vs .95**가 나온다.
**우리가 잘해서가 아니라 그 시스템이 이 과제용이 아니라서다.**

TableRAG는 검색 결과를 리더에 넘기지 않는다. ReAct 에이전트가 **전체 데이터프레임에 pandas
코드를 쓰고**, 검색은 필터 값 힌트일 뿐이다. 그래서 숫자를 개별 색인할 이유가 없다.

→ **색인 단위만 떼서 비교하면 허수아비**, **설계대로 실행하면 `table_md` 계열**(전체 표 + 코드
실행)인데 그건 이미 우리가 −3~8pp로 지고 있는 arm이다. 어느 쪽도 +10%로 가지 않는다.

### 그래도 건진 것

이 측정이 **연구 공백의 증거**다. 지금까진 "계층 표를 코퍼스 규모에서 검색한 보고가 없다"를
주장으로만 썼는데, 이제 이유를 수치로 댈 수 있다 — **대표적 셀 단위 table-RAG가 숫자 셀의
76%를 색인조차 하지 않는다.** 관련연구 절에 그대로 들어간다.

## 5. 열린 결정

1. **무대를 코퍼스 규모로 옮길 것인가.** HiTab·RealHiTBench는 표가 컨텍스트에 들어가서
   (§3.1: 표 전체 투입 시 OSC 1.0, 토큰도 더 적음) 검색이 구조적으로 이길 수 없다.
   여유가 있는 곳은 MultiHiertt 1,203표 / 43,607셀 규모. 그쪽 완전성은 이미
   **S3 set_em@50 .9564 vs flat .8826**.
2. **TableRAG 러너를 계속 지을 것인가.** 짓는다면 목적이 "이긴다"가 아니라
   **"이 과제엔 적용 불가함을 보인다"** 여야 한다.
3. **`unaligned` 592표 원인 규명.**
4. **LLM judge 추가** — table-RAG 논문들의 관행. 설계 조건: 판정자가 arm을 몰라야 하고
   (S1/S2 라벨 가림), temperature 0, 고정 프롬프트, 이진 0/1. 94문항 × 2 arm = 188콜.
