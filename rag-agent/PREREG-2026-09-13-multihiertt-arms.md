# 사전등록 — MultiHiertt 다중 조회·산술: 검색 정확도와 답변 EM (2026-09-13)

실행 **전에** 조건과 예측을 박는다. 결과를 보고 규칙을 고르지 않는다(`CLAUDE.md` §7).

## 왜 이 데이터셋인가

HiTab 주 모집단은 gold 셀이 하나라 지표가 "그 한 칸이 예산 안에 있나"로 떨어진다.
MultiHiertt 는 질의당 supporting fact 가 여러 개이고 문서 안에 표가 여럿이라, 같은
지표가 "필요한 셀을 **빠짐없이** 회수했나"를 묻는다. 그리고 `program` 필드가 조회와
산술을 데이터셋 스스로 갈라 준다 — 우리가 나눈 분류가 아니다.

## 모집단 (데이터셋 필드로만 정의)

`bevaya/MultiHiertt` **train** 분할. ⚠️ test 는 gold 를 공개하지 않고 validation 은
`lookup_m2+` 가 48건뿐이라 층이 서지 않는다. **train 을 쓰는 것은 학습이 아니라
평가다**(`CLAUDE.md` §0.3: 학습 단계 없음). 이 수치는 MultiHiertt 리더보드 수치와
같은 분할이 아니므로 **발표된 MultiHiertt 수치와 나란히 싣지 않는다**.

- `text_evidence` 가 있는 질의는 제외한다 — 문단은 셀 색인이 원리적으로 담을 수 없다.
  개수를 보고한다(계측기의 한계이지 결과가 아니다).
- `table_evidence` 좌표가 데이터 셀로 안 내려오는 질의는 **사유를 붙여 제외**하고
  개수를 보고한다.
- 층: `program` 이 비면 `lookup`, 있으면 `arith`. `m` = gold 셀 수.
  보고 단위는 `lookup_m1` / `lookup_m2+` / `arith_m1` / `arith_m2+` 넷 전부.
  **한 층만 싣는 것은 체리피킹이다.**

## 고정 조건 (arm 사이에 다른 것은 색인 단위 하나뿐)

| 항목 | 값 |
|---|---|
| 인코더 | `BAAI/bge-base-en-v1.5` (기성품, 학습 없음) |
| 검색 | hybrid α=0.7, 전수 내적 + BM25 (HiTab arm 에 고정된 값 그대로) |
| 셀 예산 | 20 (마지막 단위는 통째로 유지) |
| 리더 | `local:Qwen/Qwen2.5-7B-Instruct?quantization=4bit`, greedy, max_new_tokens=64 |
| 프롬프트 | `neutral` (표현 중립. 특정 arm 의 문장 형태를 가정하지 않는다) |
| 채점 | MultiHiertt 공식 채점기 포팅 `rag_agent/eval/multihiertt_em.py` |
| 범위 | `doc`(과제 정의, 주지표) 와 `corpus`(스트레스) 둘 다 |

## 비교군 — 무엇을 재현했고 무엇을 재현하지 않았는지

| arm | 출처 | 이 실험에서 재현한 것 | 재현하지 **않은** 것 |
|---|---|---|---|
| `cell` (본 방법, s3c) | 본 연구 | 셀+행/열 경로 문장, 제목 없으면 S2 경로 | — |
| `trag_hetero` | Huawei TableRAG, arXiv 2506.10380 | `excel_to_markdown` → `RecursiveCharacterTextSplitter(1000, 200)` → `"File name: …"` 접두 | BGE-M3·리랭커, NL2SQL 레그 |
| `tablerag` | Chen et al., NeurIPS 2024 (TableRAG) | `build_cell_corpus` + `build_schema_corpus` 문서 문자열 | 스키마/셀 채널 분리, ReAct 코드 실행 에이전트 |
| `rowcol` | 같은 논문 §4.2 (TableSampling) | 행·열 단위 인코딩 후 **교집합 부분표** | 표당 색인(`init_retriever(table_id, df)`), top_k=5 고정 |
| `chunk` | 업계 관행 (발표된 시스템 아님) | 행을 보존하는 마크다운 청킹, 청크마다 헤더 블록 반복 | — |

**어느 행도 "그 시스템을 이겼다"가 아니다.** 검색기·예산·리더·채점기를 고정하고
**색인 단위만** 갈아 끼운 비교다. 논문 표에 이 문장을 함께 싣는다.

## 예측 (실행 전에 박는다)

1. `doc` 범위 `all` 기준 본 방법 `cell` 이 `rowcol` 을 이긴다 — HiTab 에서 +.39 였고
   교집합 규칙은 데이터셋과 무관하게 셀을 적게 배달한다.
2. `m` 이 오르면 모든 arm 의 `all` 정확도가 내려간다. 내려가는 폭은 단위가 큰
   arm(`chunk`, `trag_hetero`)에서 **더 작다** — 한 단위가 여러 gold 를 동시에 담는다.
   → 즉 **다중 셀에서는 청킹이 셀 단위를 따라잡거나 이길 수 있다.** 이것이 이
   데이터셋에서 본 방법이 질 수 있는 자리이고, 지면 그대로 싣는다.
4. 검색 정확도와 답변 EM 의 간극은 산술 층(`arith_*`)에서 조회 층보다 크다.
5. `gold` 조건(근거 셀만 주입) EM 이 `retrieved` 조건보다 높다. 그 차이가
   distractor 비용이고, 그것이 검색-EM 간극의 주된 몫이다.

예측이 틀리면 틀린 대로 적는다. 2 는 본 방법이 지는 쪽을 먼저 적은 것이다.

McNemar (짝지음, 같은 질의 집합). 층별로 따로 본다. 다중비교는 Holm.

## 추가 (2026-09-13, 답변 레그 실행 **전**)

검색 레그가 끝난 뒤, 답변 레그를 돌리기 전에 박는다. 검색 결과를 보고 바꾼 것이
있으므로 무엇을 왜 바꿨는지 함께 적는다.

1. **리더 표본**: 리더가 병목이라 층마다 최대 400건만 태운다(`--stratum-cap 400`,
   `--sample-seed 20260913`). `lookup_m1` 211 / `lookup_m2+` 365 / `arith_m1` 71 은
   전수, `arith_m2+` 만 2,224 → 400. 합계 1,047건. 질의 id 를 정렬한 뒤 시드로
   뽑으므로 모든 arm 이 같은 1,047건을 받는다. 검색 정확도 표는 2,871건 전수 그대로다.
2. **범위**: 답변은 `doc` 범위만 잰다(과제 정의). `corpus` 는 전 arm .29 이하라 리더에
   태울 의미가 없다.
3. **arm 추가·교체** (검색 레그에서 드러난 것):
   - `tablerag` → `tablerag_allobj_path`. 원래 레그는 gold 해석이 arm 에 의존하는 결함으로
     2,685건만 채점했다(고침). HiTab 주 표와 같은 가장 유리한 읽기로 재실행한 것을 쓴다.
4. **gold 조건**: `cell` 레코드의 질의 집합에서 gold 셀만 s3c 문장으로 주입(리더 천장).

예측 추가:
7. 검색에서 청킹 arm 이 셀 단위보다 .12 이상 낮으므로 답변 EM 도 낮다. 단 산술 층에서는
   청크가 행 전체를 통째로 주므로 **차이가 줄어들 수 있다** — 줄면 그대로 적는다.
