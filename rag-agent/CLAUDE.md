# 1. 이 논문이 무슨 논문인가 (2026-08-30 재정의)

**계층 헤더 표를 위한 RAG다.** 무대가 RAG라는 것이 전제이고, 거기서 오는 제약
(문맥이 유한하다, 그래서 다 넣을 수 없다)이 문제를 만든다.

## 문제 정의

계층구조 표를 **통째로** 넣으면 두 가지가 깨진다.
① 표가 크면 문맥에 안 들어간다 (RealHiTBench gold 표 중앙 1,561토큰, **86%가 512 초과**)
② 격자를 평평하게 펴면 **헤더 계층이 소실된다** — `"122"`가 무엇의 122인지 사라진다.

## 파이프라인 (본 방법)

```
표          → 셀이 속한 표의 고유 라벨(제목/캡션) + 행 경로 + 열 경로 + 값
            → 문장 생성      "35~44세 > 평균 봉사시간 > 2013년: 122"
            → 임베딩 → 벡터DB 색인 (코퍼스 전체 셀)

쿼리 인입   → 쿼리 임베딩 → 벡터DB에서 유사도로 표·셀 후보 탐색
            → 검색된 문장을 쿼리에 붙여 프롬프트 구성
            → LLM 추론 및 답변
```

**주장은 "셀을 문장으로 만든다"가 아니다.** 그건 §2에서 갈라 적는다.

## 무엇이 축이고 무엇이 아닌가

- **축**: 쿼리가 들어왔을 때 필요한 표와 셀이 정확히 검색되는가
- **축**: 그 검색을 만든 문장 표현(고유 라벨 + 계층 경로)이 검색 정확도를 얼마나 사는가
- **축이 아님 (2026-09-01 폐기)**: 토큰 예산. 예산은 붙이는 리더의 성질이라 그것으로
  정규화한 비교는 색인·검색에 대한 진술이 아니게 된다. 예산/표크기 교차점 레그도 같이
  폐기했다 — "큰 표를 통째로 넣는 것보다 검색이 낫다"는 이 연구의 **무대 설정**이지
  지금 물을 질문이 아니다. 검색 비용을 맞춰야 하면 **넘긴 셀 개수**로 맞춘다.
  대상 목록은 `results/DEPRECATED.md`

# 2. MT2Net과 무엇이 다른가 (과장·축소 양쪽 전과 있음)

**"셀+헤더 선형화를 우리가 제안한다"고 쓰지 말 것** — Zhao et al. (2022)이 그 전처리
한 줄은 이미 했다. 그러나 **파이프라인은 다르고, 같은 조건에서 우리가 이긴다.**

|  | MT2Net | 본 연구 |
|---|---|---|
| 문장의 재료 | 셀 + 헤더 | **셀이 속한 표의 고유 라벨** + 행/열 경로 + 값 |
| 찾는 방식 | 쿼리+문장 concat → BERT 이진분류 | **임베딩 → 벡터DB 유사도 검색** |
| 학습 | 근거 라벨로 지도학습 필요 | 기성품 arm은 **학습 없음**, ft arm은 **오프라인 1회** |
| **질의당 비용** | 후보마다 BERT 1회 → 58,759셀에 못 씀 | **색인 1회 + ANN 조회** |
| 범위 | 질문이 속한 **문서 안** (표 ~4개) | **코퍼스 전체** (표 424 / 1,310 / 537) |
| 헤더 출처 | 데이터셋이 준 정답 구조 | **평평한 격자에서 자가복원** |

MT2Net은 사실상 **문서 내 재정렬기**이지 코퍼스 검색기가 아니다.

⚠️ **차별점은 "학습 없음"이 아니라 "질의당 비용"이다** (2026-09-03 정정).
`models/bge-base-cell-ft-*`가 생긴 뒤로 "학습 없음"은 사실이 아니고, 그대로 두면
파인튜닝 arm을 보고하는 순간 리뷰어가 모순을 짚는다. **파인튜닝은 오프라인 1회이므로
질의당 비용 구조를 건드리지 않는다** — 색인은 여전히 한 번 만들고 조회는 여전히 ANN이다.
MT2Net은 후보마다 BERT를 한 번 더 돌려야 하고 이건 파인튜닝으로 없앨 수 없는 성질이다.

**기성품 arm과 ft arm을 둘 다 보고할 것.** 무지도(no supervision) 주장을 하고 싶으면
그건 **기성품 arm이 지고 들어가는 자리**다. 하나만 싣고 유리한 쪽을 고르지 말 것.

**통제 대결에서 이겼다** — 같은 코퍼스·예산·리더·채점기로 붙였을 때
제목이 있으면 이기고(test n=769, Holm 1.6e-07 / 5.9e-11), 없으면 비긴다(AIT-QA 42:41).
**이기는 조건과 지는 조건을 실행 전에 갈라 예측했고 지는 쪽까지 맞았다.**
수치는 `RESULTS.md` §발표된 색인 단위 MT2Net.

# 3. 현재 우선순위 (2026-08-30 확정) — 이 순서를 건너뛰지 말 것

## 1단계 — 검색 정확도를 0.9대로 (지금 여기)

**모든 종류의 쿼리에서** 쿼리가 들어왔을 때 표와 셀이 정확히 검색되는지 잰다.
"모든 종류"가 핵심이다 — 지금까지의 수치는 대부분 **단일 셀 조회(m=1)** 모집단에서
나왔고, 그것은 쿼리 종류의 한 칸일 뿐이다.

갈라야 할 쿼리 축 (데이터셋이 주는 라벨):
- RealHiTBench `QuestionType`: Fact Checking / Numerical Reasoning / Data Analysis / Visualization
- RealHiTBench `SubQType`: Value-Matching / Counting / Ranking / Calculation / Comparison / Multi-hop
- HiTab·MultiHiertt: 조회 vs 산술
- 피연산자 수 m: 1 vs ≥2

**보고 형태**: 쿼리 종류 × (표 검색 정확도, 셀 검색 정확도). 한 칸으로 뭉치지 말 것 —
뭉치면 어느 종류에서 무너지는지가 사라진다.

## 2단계 — 문장 임베딩 정확도

검색이 서면, 그 검색을 만든 **문장 표현 자체**를 잰다. 고유 라벨이 얼마나 사는가,
계층 경로가 얼마나 사는가.

## 3단계 — LLM 답변 정확도 (EM)

**여기서만 EM을 판정에 쓴다.** 1·2단계의 판정은 검색 지표로 한다.

⚠️ **3단계에는 알려진 기전이 하나 있다 — 검색을 늘리면 distractor도 같이 들어온다.**
gold 셀만 48토큰 주면 EM .888, 검색으로 509토큰 주면 .604 (`RESULTS.md` §읽기 천장).
이건 오염이 아니라 측정이다. **1단계에서 OSC를 올리는 것과 모순되지 않는다** —
1단계는 "맞는 것을 넣었는가", 3단계는 "틀린 것을 안 넣었는가"라서 다른 질문이다.
**3단계에 가서 이 비용을 다루고, 1단계에서 미리 걱정해 검색을 포기하지 말 것.**

# 4.5 지표 이름 — `top`이 두 뜻으로 쓰여 왔다 (2026-09-03 확정)

**`top1`은 지표가 아니라 조건 이름이다.** "정답이 1등"이 아니라 "셀 1개를 프롬프트에
넣었다"는 뜻이다. 같은 페이지에 `R@1`과 `top1`이 있으면 반드시 헷갈린다 — 실제로
헷갈린 전과가 있다. **논문·문서 표기는 아래 왼쪽을 쓰지 말고 오른쪽을 쓴다.
코드 함수명·조건 문자열은 그대로 둔다** (원본 파일과 대조가 깨진다).

| 코드/원본 파일 | **문서·논문 표기** | 뜻 | 리더 |
|---|---|---|---|
| `R@1` `hit@1` `setEM@1` | **정답셀 1등률** | 코퍼스 전체 정렬에서 gold 셀이 1등 | 안 부름 |
| `setEM@k` | **all-covered@k** | gold 셀이 **전부** 상위 k 안 | 안 부름 |
| `top1` 조건 | **주입1** | 상위 **1개**를 프롬프트에 넣고 답하게 함 | 부름 (EM) |
| `top3` / `top10` 조건 | **주입3 / 주입10** | 상위 3개 / 10개를 넣음 | 부름 (EM) |
| `orc10` 조건 | **오라클재정렬10** | top10 안에 gold가 있으면 gold만 주입 (상한) | 부름 (EM) |
| `rr10` / `rr10_3` 조건 | **재정렬주입1 / 재정렬주입3** | top10을 재정렬 후 1개/3개 주입 | 부름 (EM) |

**두 값이 붙어 보이는 것은 우연이 아니라 인과다.** `주입1`의 EM은 `정답셀 1등률`에
리더 정확도를 곱한 값이라 항상 조금 낮다 (dev: .7193 × .9196 + .2807 × .0687 = .6807).

⚠️ **`setEM`은 exact match가 아니다.** 조건이 gold **⊆** top-k라 여분 셀에 감점이 없다.
HotpotQA의 Sup EM(예측 집합 **==** gold 집합)을 아는 리뷰어가 "EM인데 왜 정밀도가
없냐"고 묻는다. `all-covered@k`로 쓰고 "HotpotQA의 Sup EM에 대응하되 회수율만 본다"를
한 줄 단다. 원문 확인 필요: Yang et al. (2018), *HotpotQA*, EMNLP, arXiv:1809.09600 §4.

# 5. 기각된 가설 (다시 제안하지 말 것)

- **헤더 깊이가 이득을 설명한다** — 기각. 상관 −0.03 / −0.07, 버킷 비단조.
- **질문 유형(조회 vs 산술)이 MultiHiertt 무효과를 설명한다** — 기각. HiTab은 두 유형
  모두 유의, MultiHiertt는 두 유형 모두 무효과.
- **표 검색 1등/2등 점수 차로 arm을 질의마다 갈아탄다** — 기각. 신호는 유효하나
  양쪽 구간에서 한쪽 arm이 이겨서 갈아탈 대상이 없다.
- **헤더 복원 정확도를 올리면 답변이 좋아진다** — 기각. 행 경로 .80 → gold(1.0)로
  올려도 EM 무변화(dev p=.7266, train p=1.0). 여기 시간 쓰지 말 것.
- **셀 문장을 자연어로 다듬으면 오른다 / 어순을 바꾸면 오른다** — 기각. n=830에서 확정.
  S2 .517 / S2r .527 / MT2Net .516이 서로 구별되지 않는다(p=.56 / p=1.00).
  버는 것은 문장 형태가 아니라 **고유 라벨**이다.
- **단위를 문장에 명시하면 형식 오류가 준다** — 기각. 헤더 경로에 이미 38.2%,
  퍼센트성 셀만 보면 96.1%가 적혀 있다.
- **제목을 표당 한 번만 쓰고 자리를 아낀다(`group` arm)** — 기각. 자리는 남고 OSC도
  오르지만 EM은 안 움직인다.
- **표당 셀 수를 제한해 형제 혼동을 줄인다(`capped` arm)** — 기각. 세 예산 모두 악화.
  혼동의 원인은 "형제"가 아니라 **총량**이다.
- **제목이 없는 코퍼스에 제목을 생성해 붙이면 오른다** — 기각 (2026-08-27, 사전 등록
  `PREREG-2026-08-27-generated-title.md`). 주소 중복은 깎였으나(30.1% → 19.6%)
  EM이 .3082 → .2239로 유의하게 떨어진다(33:71, p=.0002).
  → **고유 라벨의 이득은 "이름이 있다"가 아니라 데이터셋이 준 이름의 내용에 있었다.**
- **표 하나로 좁히면(`cascade`) 혼동이 준다** — S2에서는 맞고 S3에서는 뒤집힌다.
- **열 경로 BM25를 가산해(`--col-boost`) 정답셀 1등률을 올린다** — 기각.
  β=0 **.6819** → .1 .6687 → .3 **.6241**로 단조 악화
  (`results/colboost/*_cb{0.0,0.1,0.3}_ranks.jsonl`, dev 830, a0 α=1.0).
  열 경로는 표를 건너뛰면 generic 텍스트라 무관한 표의 셀을 같이 끌어올린다.
- **기성품 크로스인코더(`bge-reranker-*`)를 얹어 R@1을 올린다** — 기각 (2026-09-03,
  사전등록 `PREREG-2026-09-03-ce-rerank-r1.md`, 판정 `results/rerank/VERDICT.md`).
  파인튜닝된 `p0` 위에서 hit@1 **.7193 → .6181**, EM **−.1289**. 1등 승격 67 대
  강등 151 (p=1.26e-08). ⚠️ **정렬 오류가 아니다** — 무작위 기준선 .0945 대비 .6181로
  신호는 있고, **도메인 내 학습된 bi-encoder를 무학습 범용 리랭커가 못 이기는 것**이다.
  같은 리랭커가 **기성품** bi-encoder 위에서는 도움이 됐다(`RESULTS.md` §11, +.037).
  **두 수치를 같은 문장에 쓰지 말 것.**
- **재정렬 후 상위 3개를 주면 회수를 지키며 distractor를 깎는다** — 기각. `rr10_3`
  .6795가 `top3` .7157에 진다(56:86, p=.0147). 깎는 것은 재정렬이 아니라 **자르기**다.

# 6. 현재 최선

> 코퍼스 전체 셀 인덱스 + 셀 문장(고유 라벨 + 행 경로 + 열 경로 + 값).
> 표에 **고유 라벨이 있으면** 그것까지(S3), 없으면 경로만(S2). = **`S3c`**

구조적 장치(`group` 묶기, `capped` 제한, `cascade` 집중)는 **전부 이 문장 하나에 졌다.**

# 7. 실행 규칙

- **검색기는 `hybrid` α=0.7** (2026-08-27 변경, 2026-08-30 4/4 확인).
  네 코퍼스 전부에서 dense를 이긴다. 단 **α 값 자체는 임의다** — 0.5와 0.7이 세 코퍼스에서
  구별되지 않는다. 레버는 α가 아니라 하이브리드냐 dense냐이므로 α를 코퍼스마다 튜닝하지 말 것.
  ⚠️ **dev에서만 확인됐다. test는 dense로만 돌렸다.**
- **셀 스킴은 `S3c`.** 새 실험을 S2로 돌리지 말 것 — S2는 논문의 index unit이 아니다.
  (`_h2h_` 파일의 `cell`/`cascade` arm은 S2다. 우리 arm은 `_s3_`·`s3c_`에서 읽는다.)
- **산술 모집단에 로컬 7B를 쓰지 말 것.** 전 arm EM .02~.06이라 방법이 아니라 리더를
  재는 실험이 된다. 산술 레그는 계산 되는 리더로만 돌린다.
- **답변 레그 재실행은 `--out`을 새 경로로.** `runenv.guard_resume`이 이어붙이기를 막는다.
- **짝지음은 `flat` arm부터 확인.** flat은 템플릿을 안 읽으므로 움직이면 리더·환경이
  교란된 것이다. 판정은 **"불일치 ≤5이고 p가 유의하지 않음"**.
- **파이프 뒤의 `$?`를 믿지 말 것.** `${PIPESTATUS[0]}`와 결과 파일 존재를 같이 본다.
- **개입은 예측을 먼저 커밋하고 시작한다.** `PREREG-*.md`에 숫자로 박고 실행한다.
  결과를 보고 규칙을 고르는 것은 이 저장소가 금지한다.
- **RealHiTBench 전용 플래그** — `--population rhb_nr_all`만 주면 코퍼스가 기본값으로
  만들어져 동결 대조에 실패한다. `--rhb-question-types` / `--rhb-em-only`를 같이 줄 것.

# 8. 오염된 결과 — 인용 금지 / 단서 필수

- **RealHiTBench의 모든 OSC·셀 검색 수치** (2026-08-30 확인). RHB는 gold 셀 주석이
  없어서 **답 문자열을 셀 값과 매칭해 gold를 복원**한다. 답이 계산값이면 무관한 셀에
  유일하게 걸린다. 전수 감사 결과 **231건 중 61건(26.4%)** 이 질문과 gold 셀 경로가
  내용어를 하나도 공유하지 않고, **실패 96건 중 51건(53.1%)** 이 그렇다.
  → RHB 셀 검색 수치는 **하한이지 성능이 아니다.** 근거 `results/gold_label_audit_realhitbench.jsonl`.
  같은 기전으로 **AIT-QA도 451건 중 34건(7.5%)** 이 오염 — 정도는 훨씬 낮다.
  HiTab·MultiHiertt는 gold 셀이 실제 주석이라 해당 없음.
- **RealHiTBench `rhb_lookup_all` 모집단이 "조회 쿼리"라는 서술** — 사실이 아니다.
  QuestionType 기준 Fact Checking 164 / Numerical Reasoning 54 / Data Analysis 11 /
  Visualization 2가 섞여 있다. 순수 조회는 SubQType `Value-Matching` 114건이다.
- **2026-08-26 이전의 AIT-QA EM 전부** — 채점기가 `$`를 못 벗겨 약 6점 낮다.
- **2026-08-26 이전의 RealHitBench 수치** — 모집단 243 → 231. 이후 것과 짝지을 수 없다.
- **n=100 표본의 템플릿 대조** — S2/S3/MT2Net을 가르지 못한다. 양쪽으로 뒤집힌 전과.
- **단일 셔플 순열 수치** — 평균과 범위로만 쓴다.
- **NM(±2%)·`em_norm`** — 진단 전용. 리더보드 비교 금지.
- **SMART / ASTRA 등 2026년 인접 연구와 같은 표에 올리기** — 표가 주어지고 검색이 없다.
- **`RESULTS.md` §검증된 외부 사실 목록 밖의 MT2Net·MultiHiertt 수치 생성.**
- **대소문자 뭉갬을 어떤 결과의 설명 요인으로 쓰기** — 인코더가 `do_lower_case=True`.
- **"헤더 복원을 고쳐서 정확도를 올렸다"** — 고친 것은 버그이고 EM은 +.009 n.s.다.
- **파인튜닝 인코더 수치를 청킹 정책 표(P1~P4)에 올리기.** 정책 레그는 전부 기성품
  `BAAI/bge-small-en-v1.5`로 측정됐다(`results/FINAL_TABLE.md` 공통 조건). 거기에
  a0/p0 수치를 넣으면 **청킹 정책 효과와 표현학습 효과가 섞인다** — 이미 지적된
  `table_md` 대 `path_cell` 교란과 같은 구조다. 정책 비교는 기성품 고정, 파인튜닝은
  S3c 고정한 채 arm끼리만. **두 절은 인코더가 다르며 교차 비교하지 않는다고 논문에 명시할 것.**
- **`hitab_train_sel_lookup_all`(756) 수치를 성능으로 보고하기.** sel은 **질의만**
  held-out이고 **표는 학습 때 본 표**다 (`fit` 2,914 ∩ `sel` 759 = 0 이지만 둘 다 같은
  train 코퍼스 2,043표를 쓴다). 그래서 sel 이득은 낙관적이다 — p0는 sel +.0502,
  표가 새것인 dev에서 +.0301로 줄었다. **sel은 α 선택용이라고 명시하고 쓸 것.**
