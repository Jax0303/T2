# 사전등록: TableRAG (NeurIPS'24) 를 그쪽 설정에서 공정하게 다시 잰다 (2026-09-10)

## 왜 다시 재는가

현행 표 1·2 의 TableRAG (NeurIPS'24) 두 행(검색 .0686/.1433, 답변 EM .0262/.0434)은
**그 시스템이 구현하지 않는 설정에서 잰 값이다.** 공식 코드
(`google-research/table_rag/agent/retriever.py`)의 `init_retriever(table_id, df)` 는
호출될 때마다 `db_dir = f'{data_type}_db_{max_encode_cell}_' + table_id` 로 FAISS
인덱스를 **표마다 하나씩** 세우고 `top_k=5` 로 그 안에서만 검색한다. 코퍼스 단위
인덱스가 파일 어디에도 없다 — **TableRAG 는 표를 가로질러 검색하지 않는다.**
우리는 538표를 한 코퍼스에 넣고 검색시켰다. 그 수치로 "우리가 이겼다"고 쓸 수 없다.

이 실험은 그 부당함을 제거한다. **결과가 어느 쪽으로 나오든 그대로 싣는다.**

## 세 가지 부당함 중 이 실험이 고치는 것

    1. 표를 가로질러 검색시킴        → 고친다 (`--corpus gold`)
    2. 검색 결과를 리더에게 넘김      → 고치지 않는다. 대신 **해결기를 고정**하고
                                       "색인 단위 비교"라고 명시한다 (아래 §주장 범위)
    3. 계층표를 flat frame 으로 변환  → 고칠 수 없다(그쪽 전제다). leaf/path 둘 다 싣는다
    +  `build_schema_corpus` 누락    → 고친다 (범주형 열 스키마 문서 추가)

## 개입

- **`--corpus gold`**: 코퍼스는 split 538표로 그대로 짓되, 질의마다 **자기 표의 색인
  단위만** 후보로 둔다. dense 레그에는 표별 인덱스와 정확히 같다(코사인은 문서별).
  sparse 레그는 IDF 가 코퍼스 전역이라 근사인데, TableRAG 자신이 dense-only 이므로
  네이티브 조건(`--alpha 1.0`)에서는 이 근사가 아예 사라진다.
- **`build_schema_corpus` 보강**: 범주형 열마다 `{"column_name","dtype","cell_examples"}`
  문서를 추가한다(TableRAG 의 최빈 3개). 셀을 0개 배달하므로 **예산을 전혀 쓰지 않고**,
  표를 찾는 데만 도움이 된다 — TableRAG 에게 유리하게만 작용한다.
- **`--max-units`**: TableRAG 의 `top_k=5` 는 셀 5개가 아니라 **문서 5개**다. 네이티브
  조건에서 그 정지 규칙을 쓴다.

## arm (전부 test 1,581, 리더·프롬프트·디코딩·채점기 동일)

    G1  본 방법 (셀 문장)      gold 표 주어짐, hybrid a=0.7, 예산 20
    G2  TableRAG leaf         gold 표 주어짐, hybrid a=0.7, 예산 20
    G3  TableRAG path         gold 표 주어짐, hybrid a=0.7, 예산 20
    N1  TableRAG leaf 네이티브  gold 표 주어짐, dense-only a=1.0, top_k=5 문서  (검색만)
    N2  TableRAG path 네이티브  gold 표 주어짐, dense-only a=1.0, top_k=5 문서  (검색만)
    N0  본 방법 dense-only     gold 표 주어짐, a=1.0, 예산 20                  (검색만)
    X   본 방법, 코퍼스 검색    (기존 수치 재사용, 재실행 없음) 검색 .9142 / 답변 .7164

G1~G3 는 답변 EM 까지 낸다. N1·N2·N0 는 검색 정확도만 낸다 — 정지 규칙이 달라
답변 비교에 넣으면 예산이 섞이기 때문이다.

## 두 개의 비교, 두 개의 다른 주장

- **대칭 비교 (G1 vs G2/G3)**: 양쪽 다 gold 표를 받고, 같은 검색기·같은 예산·같은
  리더. 유일한 차이가 **색인 단위**다.
- **상대에게 오라클 (X vs G2/G3)**: TableRAG 에는 gold 표를 **그냥 주고**(코퍼스
  설정에서 절대 넘을 수 없는 상한), 우리는 538표에서 진짜로 검색한다.
  **여기서도 우리가 이기면 "깎아내렸다"가 성립하지 않는다.**

## 주장 범위 (실행 전에 못 박는다)

- 이 실험이 허락하는 문장: *"그쪽 자신의 표별 설정에서, 해결기·예산·채점기를 고정했을
  때 TableRAG 의 색인 단위는 계층표 QA 가 필요로 하는 셀을 배달하지 못한다."*
- **허락하지 않는 문장: "우리가 TableRAG 를 이겼다."** TableRAG 는 검색 결과를 근거가
  아니라 **pandas 코드용 힌트**로 쓰고 표 전체를 ReAct 에이전트에게 넘긴다. 그 에이전트를
  재현하지 않았으므로 시스템 대 시스템 비교가 아니다. 재현하면 산술 216문항에서 우리가
  질 공산이 크다는 것도 함께 적는다.
- leaf 만 이기고 path 에 지면 결과로 쓰지 않는다. **둘 다 싣는다.**

## 예측 (실행 전 고정)

- G2/G3 의 검색 정확도는 .0686/.1433 에서 **크게 오른다** — 표가 주어졌으니 당연하다.
- 그럼에도 **G1 이 G2·G3 를 크게 이길 것으로 예측한다.** 근거는 표를 찾는 단계가 아니라
  색인 단위다: TableRAG 는 숫자 열을 min/max 요약 **문서 하나로 접고 개별 숫자를
  인코딩하지 않는다**(`tablerag_unit.py` 머리, 공식 코드 대조 완료). 계층표 질의의
  피연산자는 거의 다 숫자 셀이므로 표를 줘도 그 셀은 닿지 않는다.
- 구간 예측: G2/G3 검색 정확도 주지표 **[.15, .45]**, 답변 EM **[.05, .25]**.
  이 밴드를 벗어나면 예측이 빗나간 것으로 적는다.
- **X vs G2/G3 에서 우리가 지면 그대로 보고하고 표 1·2 의 해당 행을 전부 내린다.**

## 고정

- 기준 커밋 62f57df. 리더 `local:Qwen/Qwen2.5-7B-Instruct?quantization=4bit`,
  temperature 0, seed 42, max_new_tokens 64, batch 1, 프롬프트 `BASE`.
- 인코더 `BAAI/bge-base-en-v1.5`, 학습 없음. 채점 `hitab_exact_match_text`.
- 모집단은 기존 정의 그대로 — 주지표 단일 셀 조회 991, 데이터셀 전체 1,245, 헤더답 336.
- 코드 변경은 기존 arm 을 바꾸지 않아야 한다. **회귀 검사**: `--corpus split` 로 s3c 를
  다시 돌려 `accuracy_all_mode 0.89 / any 0.8452 / gold_table 0.9538` 재현 확인
  (2026-09-10 통과).
